# 피그마 → 퍼블리싱 코드 생성 (웹/기본 버전)

> 스킬 버전: 5.3.0 — 이 줄의 버전 번호가 최신인지 확인하세요. 다른 대화창/세션에서 작업한 버전과 다르면 아직 동기화가 안 된 것입니다.

## 최우선 원칙: 유추하지 않는다, 확인한다

**이 스킬 전체를 관통하는 단 하나의 원칙이다.** 색상, 크기, 위치, 회전, 배경, 정렬, 여백, 반응형 여부 등 **어떤 값이든** "이 정도면 맞겠지", "저쪽이 이러니 이쪽도 비슷하겠지", "보통 이런 건 이렇게 하니까"로 채워 넣지 않는다. 아래는 실제로 이런 유추 때문에 생긴 사고들이다 — 전부 "직접 확인했으면 안 생겼을" 문제다:
- 배경이 있는 카드 옆에 비슷한 카드를 만들면서 배경을 빠뜨림
- 왼쪽 버튼을 회전시켜 오른쪽 버튼도 그럴 거라 가정하고 위치/회전을 안 맞춰봄
- 아이콘 크기를 어림잡아 140px처럼 대충 채워 넣음
- 여백이 있어야 할 것 같아서 근거 없이 padding을 추가하거나, 반대로 없앰
- 이전에 만든 페이지의 아이콘과 비슷해 보여서 그 코드를 그대로 재사용

**이 스킬의 모든 세부 규칙(속성 1:1 보존, 노드 완전성 확인, 치수표 작성 등)은 결국 이 원칙 하나를 구현하는 방법일 뿐이다.** 값 하나라도 확신이 안 서면, 진행하지 말고 그 부분을 실제로 다시 조회해서 확인한다.

**이 스킬은 웹(기본) 버전을 만드는 것까지만 담당한다. 태블릿/모바일 반응형은 `pub-responsive` 절차로 넘긴다.** 작업 시작 시 1-4에서 일반/반응형을 먼저 명확히 구분하고, 반응형이면 사용자가 별도 명령을 입력할 필요 없이 이 흐름 그대로 `pub-responsive`의 절차로 자동 이어간다.

## 사용자에게 질문할 때 (전체 공통)

이 스킬에서 나오는 모든 선택형 질문(영역 선택, 새/기존 페이지 선택, 파일 선택 등)은 **반드시 `AskUserQuestion` 도구를 사용**한다. 그냥 텍스트로 나열만 하고 타이핑으로 답하게 하지 않는다.
- **질문 문구와 선택지 라벨은 한글로 작성한다.** `main.html`, `sub.html` 같은 실제 파일명 자체는 영문 그대로 두되, 그 옆에 한글 설명을 병기한다.
- `AskUserQuestion`의 "Type something." / "Chat about this" 같은 고정 UI 문구는 도구 자체의 고정 표시라 스킬로는 바꿀 수 없다.

## 작업 전제

- 이 스킬은 반드시 실제 프로젝트 폴더 안에서 실행 중인 Claude Code 세션에서 사용한다.
- **작업 폴더 안에 영역이 명확할 때만 그 폴더가 곧 "영역"이다.** 상위 폴더에 web1/web2/bcnimda처럼 여러 영역이 함께 있으면 자동으로 정하지 말고 반드시 사용자에게 먼저 물어본다.
- layout.css, design.css는 실제 파일이다. git으로 커밋되면 다른 퍼블리셔와 자연스럽게 공유된다.

## 작업 절차

1. **아래 순서를 매번 무조건, 하나씩 순서대로 진행한다.**

   **1-1. 영역 확인**
   - 항상 지금 Claude Code 세션이 실행된 현재 폴더를 기준으로 진행한다. "실제 프로젝트 폴더 경로를 알려달라"거나 다른 폴더로 옮겨서 작업하자는 식으로 되묻지 않는다.
   - 현재 폴더 또는 `inc/` 아래에 이미 만들어진 영역 폴더가 있으면, 그 이름을 선택지로 제시하고 "기타(직접 입력)"도 함께 제시한다.
   - 영역 폴더가 하나도 없어도 마찬가지로 현재 폴더에서 바로 물어본다.
   - 지금 실행 위치가 이미 특정 영역 폴더 안이라 다른 후보가 아예 없을 때만 예외적으로 이 단계를 묻지 않는다.

   **1-2. 새 페이지인지 기존 페이지인지 확인**
   - `html/{영역}/` 폴더 안의 파일 목록을 실제로 조회한다. 폴더가 없거나 비어 있으면 새 페이지로 진행. 파일이 하나 이상 있으면 반드시 물어본다: "새 페이지를 만들까요, 아니면 기존 페이지에 이어서 작업할까요?"

   **1-3. (기존 페이지인 경우) 대상 파일 선택**
   - 파일 목록을 `AskUserQuestion`으로 제시해서 화살표 키로 고를 수 있게 한다. 10개 이상이면 이름 검색으로 먼저 좁힌다.

   **1-4. 일반/반응형 구분 + 피그마 프레임 지정 확인 + (새 페이지인 경우) 파일명 자동 결정**
   - **가장 먼저 `AskUserQuestion`으로 명확히 구분해서 물어본다**: "이번 작업은 일반(웹 버전만)인가요, 반응형(웹+태블릿+모바일)인가요?" — 사용자의 원래 요청에 "반응형", "태블릿", "모바일" 같은 말이 이미 있었다면 그 답이 명확하니 다시 묻지 않고 바로 그쪽으로 진행한다.
     - **일반이면**: 아래 순서대로 이 스킬(`/pub`) 안에서 계속 진행한다. 웹 피그마 링크를 물어본다('Copy link to selection'으로 복사한 node-id 포함 링크).
     - **반응형이면**: 사용자에게 별도 명령을 다시 입력하라고 시키지 않는다. **이 흐름 그대로, `pub-responsive` 스킬(`/mnt/skills/.../pub-responsive/SKILL.md` 또는 해당 플러그인 경로)의 절차를 이어서 그대로 따른다** — 사용자 입장에서는 `/pub` 한 번 실행한 것으로 끝까지 이어지는 것처럼 보여야 한다. 다만 웹 버전 생성(1~6번, 고정 규칙)까지는 이 스킬대로 하고, 그 다음 반응형 단계(웹→태블릿→모바일 순차, 완전 대조, 커버리지 표 등)부터는 `pub-responsive`에 정의된 절차와 형식을 그대로 적용한다. 두 스킬의 규칙을 다르게 섞어 쓰지 않는다 — 반응형 부분은 전적으로 `pub-responsive`의 규칙을 따른다.
   - **같은 프레임을 다시 요청받으면 기본적으로 "재검증 후 수정" 모드로 동작한다.** 기존 구현이 있으면, **같은 세션의 자기 점검이 아니라 `figma-review-agent`(Opus, 독립 컨텍스트)를 Task 도구로 호출해서 재검증한다.** 방금 만든 걸 만든 사람이 다시 봐서 "문제없다"고 넘기는 걸 막기 위해서다. 검증에서 문제가 나오면 그 부분만 고친다. "처음부터 다시 만들어줘"일 때만 완전 재생성.
   - **새 페이지인 경우, 파일명을 따로 물어보지 않고 프레임 이름 기반으로 자동 결정한다.**
     - 메인/대표 페이지는 `index.html`이 아니라 `main.html`.
     - `sub.html`, `list.html`, `detail.html`처럼 구분 안 되는 이름 금지 — 프레임 이름 반영해서 구체적으로.
     - 겹치면 더 구체화. 자동 결정 후 "이 이름으로 만들었어요, 마음에 안 들면 말씀해주세요" 정도로만 안내.

   **공통 규칙**
   - **한 번 확인된 항목은 다시 묻지 않는다.** 단, 이 범위는 지금 실행 중인 `/pub` 한 번의 호출 안에서만이다 — `/pub`을 다시 실행하면 매번 새 작업으로 취급하고 1-1부터 다시 시작한다.
   - 확인 완료되면 `inc/{영역}/css/`, `html/{영역}/`, `files/{영역}/images/common/` 구조가 없을 경우 생성한다. 별도로 안 물어봐도 된다.
   - **작업 도중 영역 전환** 요청이 오면 즉시 전환하고 1-2부터 다시 진행, 이전 영역과 안 섞이게 한다.
2. 확인된 영역 기준 `layout.css`, `design.css`를 찾는다.
   - **토큰 최적화**: design.css가 크면 관련 키워드로 grep해서 관련 블록만 확인, 전체를 매번 읽지 않는다(300줄 이하이거나 첫 실행/대개편일 땐 전체 확인).
   - 폴더/파일이 없으면 새로 만든다.
3. 연결된 Figma 도구로 `$ARGUMENTS`로 받은 링크의 프레임을 분석한다.
   - **공통 레이아웃(GNB/LNB/헤더/푸터) — 서브 페이지에만 적용**: GNB/LNB/헤더/푸터가 포함돼 있으면 다시 분석해서 새로 만들지 않는다. 메인 페이지(`main.html`)는 이 규칙 예외 — 항상 피그마 메인 프레임 기준으로 그대로 만든다. 재사용 범위는 `<header>`/`<nav>`/`<footer>` 태그나 `gnb`/`lnb`/`header`/`footer`/`nav` 클래스로 식별되는 요소로 엄격히 한정하고, 다른 콘텐츠 섹션을 같이 끌어오지 않는다. 기존 서브 페이지에서 grep으로 그 부분만 찾아 복사, 없으면 이번에 만들고 "기준 버전"이라고 안내. 디자인이 달라 보이면 임의로 새로 만들지 말고 확인.
   - **노드 완전성 확인(필수)**: 스크린샷엔 보이는데 참고 코드에 없는 시각 속성(테두리/배경/그림자)이 있으면 부모 노드 누락을 의심하고 부모까지 포함해서 다시 조회한다.
   - **속성 1:1 보존(필수)**: border, background, border-radius, box-shadow, 정확한 색상/변수, padding/gap 수치를 하나도 빠짐없이 그대로 옮긴다. 프레임워크 문법만 걷어내고 구조/수치는 유지. **`border-radius`가 네 모서리 전부가 아니라 특정 모서리 하나(예: `rounded-bl-[280px]` = 왼쪽 아래만)만 지정된 경우를 놓치지 않는다** — 참고 코드에 `rounded-tl/tr/bl/br` 같은 개별 모서리 클래스가 있으면 `border-top-left-radius` 등 해당 모서리 속성만 정확히 옮긴다.
   - **고정 폭(px)과 유동 분할(`flex:1 0 0`)을 서로 바꿔치기하지 않는다(필수).** 둘 다 "형제 요소들이 나란히 배치된다"는 점에서 겉보기엔 비슷해 보이지만 실제 동작은 다르다 — 참고 코드가 고정 `width: 597px` 같은 값이면 그대로 고정폭으로 옮기고, 참고 코드가 `flex: 1 0 0`(균등 분할)이면 그대로 flex로 옮긴다. "이 정도면 비슷하게 나오겠지"로 임의 대체하지 않는다(실제 사례: 고정 597px여야 하는 카드 두 개를 `flex:1 0 0`으로 잘못 바꿔서, 콘텐츠 양에 따라 카드 크기가 원본과 다르게 나온 사고가 있었다).
   - **부모-자식 그룹핑 구조 보존(필수)**: 참고 코드에서 형제로 같이 있는 요소는 구현에서도 반드시 같은 부모 안에 형제로 둔다. 값은 맞아도 그룹 구조가 달라지면 레이아웃이 어긋난다.
   - **`align-items`를 빠뜨리면 자식이 원치 않게 늘어난다(필수 확인).** 참고 코드의 `flex` 부모에 `items-start`/`items-center`/`items-end`가 있는데 빠뜨리면 기본값(`stretch`)이 적용돼서 자식이 부모 크기만큼 늘어난다. 자식 크기가 이상하면 부모의 `align-items`부터 확인한다.
   - **`flex-direction: column`을 레이아웃 기본값처럼 습관적으로 쓰지 않는다.** 세로로 쌓인 배치를 볼 때마다 일단 `display:flex; flex-direction:column;`부터 쓰고 보는 습관이 있으면, `align-items`를 빠뜨려서 자식들이 전부 `width: 100%`처럼 늘어나는 사고가 반복된다. `flex-direction: column`을 쓸 때는 **그때마다 반드시** 참고 코드의 `align-items` 값을 같이 확인해서 명시한다 — "일단 column으로 잡고 나중에 정렬 확인"이 아니라 두 속성을 항상 같이 세트로 정한다.
   - **이전/다음, 좌/우처럼 짝을 이루는 요소가 서로 완전한 대칭(거울 관계)일 거라고 가정하지 않는다(필수).** 같은 아이콘을 재사용하면서 한쪽만 `rotate`/`scaleX(-1)` 등으로 반전시키는 패턴이 흔한데, 이때 "왼쪽이 이러니 오른쪽은 그 반대겠지"로 유추해서 만들지 않는다. 위치(순서, `left`/`right`), 회전 값, 아이콘 방향을 **양쪽 다 참고 코드에서 각각 직접 확인**한다 — 실제로 위치나 회전이 예상과 다르게 디자인된 경우가 있었다.
   - **레이어 이름이 아니라 실제 좌표(x/y)로 좌우/위치를 판단한다(필수, 실제 사고 사례 있음).** 피그마 레이어 이름이 "Left"/"Right", "prev"/"next"처럼 방향을 나타내도, 그 이름이 실제 좌표와 다를 수 있다(디자이너가 이름을 안 맞춰뒀거나 나중에 위치만 바꾼 경우) — 실제 사례로 "Right navigation arrow"라는 이름의 레이어가 `x=0`(왼쪽)에, "Left navigation arrow"가 `x=1324`(오른쪽)에 있던 적이 있었다. 이름만 보고 배치하면 좌우가 뒤바뀐다. `get_metadata`나 `get_design_context`로 받은 **실제 x좌표를 비교해서** 어느 게 왼쪽/오른쪽인지 판단하고, 이름은 클래스명 짓는 데만 참고한다(위치 판단 근거로 쓰지 않는다).
   - **정확한 값은 추측하지 않고 변수 정의를 조회**: 애매한 색상/이펙트는 `Figma:get_variable_defs`로 확인, 눈대중 금지.
   - **토큰 최적화**: Figma 도구는 항상 특정 프레임/노드 하나만 지정해서 조회, 페이지/파일 전체 조회 금지.
   - **"프레임이 너무 커서 뼈대만 반환됐다"는 경고를 절대 무시하지 않는다(필수).** `get_design_context` 응답 끝에 "design was too large... sparse metadata response... call get_design_context on the IDs of the sublayers" 같은 경고가 붙어 있으면, 그 응답엔 색상/폰트/정확한 스타일 정보가 없고 **구조와 좌표만 있는 뼈대**라는 뜻이다. 이 상태로 절대 진행하지 않는다. 사용자가 준 링크가 페이지 전체 같은 거대한 프레임을 가리킬 때 이런 일이 생긴다.
     1. 받은 뼈대 메타데이터에서 실제로 필요한 부분에 해당하는 **하위 레이어 이름**(예: `_Top`, `_tit`, `_right`)을 찾는다. 사용자가 요청한 내용(스크린샷, 설명)과 이름이 맞는 하위 레이어를 고른다.
     2. 그 하위 레이어의 노드 ID로 `get_design_context`를 **다시** 호출한다.
     3. 그래도 또 "너무 크다"는 경고가 나오면, 한 단계 더 작은 하위 레이어로 쪼개서 반복한다 — 실제 스타일 정보가 담긴 응답을 받을 때까지 계속한다.
     4. 여러 하위 레이어로 나눠 조회했다면, 최종적으로 각 조회 결과를 조합해서 하나의 완성된 화면으로 만든다.
   - 이 확인 없이 뼈대 데이터만으로 만든 결과물은 색상/폰트/정확한 크기가 다 틀리고 반응형도 제대로 안 된다 — 이게 "피그마를 제대로 못 읽는다"는 문제의 흔한 원인이다.
   - **차트/그래프류, 그리고 복잡한 장식용 그래픽 다발은 예외 — 먼저 물어본다**: 방사형/도넛/막대/선 그래프뿐 아니라, 배너처럼 여러 개의 겹쳐진 순수 장식 SVG(리본, 별, 블롭 등)가 절대좌표로 다닥다닥 배치된 경우도 SVG 인라인을 자동 적용하지 않는다. **이 예외는 "그 그래픽 요소 하나(또는 한 묶음) 자체가 구조적으로 복잡한지"를 보는 것이지, "페이지 전체에 아이콘이 몇 개나 있는지"가 아니다.** 화살표/체크/플러스 같은 단순 개별 아이콘이 페이지에 아무리 많아도 이 예외 대상이 아니다 — 위 SVG 인라인 규칙 그대로 각각 인라인 처리한다. "SVG로 각각 코딩할지, 통 이미지로 대체할지" 먼저 확인한다. 나중에 슬라이드/캐러셀로 바뀔 예정이면 통 이미지를 강하게 권장한다. 이미지로 결정되면 개별 요소를 쪼개지 않고 통 이미지 하나로 처리(로고/텍스트/버튼 등 실제 콘텐츠는 기존 규칙대로 마크업).
4. 아래 [고정 규칙]에 따라 HTML을 생성한다.
   - **`<body>` 바로 아래에는 전체를 감싸는 `<div id="wrapper">` 하나를 넣는다.** 헤더/GNB, 콘텐츠, 푸터가 `<body>` 밑에 각자 형제로 따로 떠 있지 않게, 이 셋을 전부 `#wrapper` 안에 넣는다. (예: `<body><div id="wrapper"><header>...</header><main>...</main><footer>...</footer></div></body>`)
   - **GNB/헤더/푸터처럼 문서 흐름을 따라야 하는 최상위 요소를 `position: absolute` + 고정 캔버스 폭으로 옮기지 않는다(필수).** 피그마 참고 코드가 이런 요소를 절대좌표로 내려주는 경우가 있는데, 그대로 옮기면 문서 흐름에서 완전히 빠지고 실제 뷰포트보다 좁은 화면(캔버스 폭과 뷰포트 폭이 다른 모든 경우)에서 어긋나거나 가로 스크롤이 생긴다. 이런 요소는 일반적인 문서 흐름(`position: static`, `width: 100%`)으로 만든다 — 실제로 겹쳐야 하는 특별한 이유(오버레이 등)가 명확할 때만 `position: absolute/fixed`를 쓴다.
   - **배너/히어로처럼 너비를 유동(`width: 100%`)으로 만드는 섹션은, 기본(데스크톱) 상태부터 높이도 같이 유동으로 만든다(필수).** 너비만 `100%`로 하고 높이는 원래 캔버스 기준 고정 px(예: `height: 600px`)로 남겨두면, `max-width`보다 좁고 다음 브레이크포인트보다는 넓은 중간 구간에서 비율이 어긋나 배경/이미지가 늘어나거나 잘려 보인다(실제 사례 있음). 기본 상태부터 `height: auto; aspect-ratio: {원래 가로}/{원래 세로};`로 만들어서, 반응형 오버라이드가 없는 구간에서도 비율이 항상 유지되게 한다. 태블릿/모바일 전용 오버라이드에만 `aspect-ratio`를 넣고 기본 상태를 빠뜨리지 않는다.
   - **CSS 작성 전에 치수표를 먼저 만든다(필수, 추가 API 호출 없이 3번에서 받은 데이터로).**
     ```
     | 요소 | 너비 | 높이 | 비고 |
     |---|---|---|---|
     | 프로필 카드 | 475px | 416px | 고정 |
     ```
   - 여러 컬럼이 나란히 배치된 레이아웃이면, 컬럼별 (높이 합 + gap 합)이 서로 맞는지 CSS 작성 전에 미리 계산한다.
   - 요소가 한두 개뿐인 단순한 프레임이면 표를 간단히 줄여도 된다.
5. **1-3(기존 페이지) 또는 1-4(새 페이지)에서 확인/결정한 파일에 저장한다.** (다시 안 물어봄) `html/{영역}/`에 저장, `layout.css`/`design.css` 실제 갱신, 이미지는 `files/{영역}/images/common/`. **JS가 필요하다고 요청받았으면 `inc/{영역}/js/design.js` 하나에 모아서 작성한다** — `design.css`처럼 영역당 JS도 파일 하나로 통일한다(페이지/컴포넌트마다 별도 JS 파일을 새로 만들지 않는다). 이미 `design.js`가 있으면 그 파일에 이어서 추가하고, 없으면 새로 만든다. (공용 라이브러리는 기존 `inc/lab/js/` 그대로 사용.)
   - **`design.js`는 그 영역의 여러 페이지(메인, 서브 등)가 공유하는 파일이므로, 특정 페이지에만 있는 요소를 다루는 코드는 그 요소가 없는 다른 페이지에서 에러 없이 조용히 넘어가야 한다(필수).** `querySelector`로 가져온 요소가 없으면(`null`) 그 블록을 건너뛰게 방어 코드를 넣는다(예: `const el = document.querySelector('.main-hero__play-btn'); if (el) { el.addEventListener(...); }`). `null`인 요소에 바로 메서드를 호출해서 에러가 나면, 그 아래에 이어지는 다른 페이지용 코드까지 같이 멈추기 때문이다. 여러 기능을 한 파일에 모을수록 이 방어 코드가 더 중요해진다.
6. 자기 점검 후 결과를 보고한다.

## layout.css가 비어있는 첫 실행일 때

피그마에서 다음을 먼저 뽑아 `:root` 토큰으로 확정한다: 가장 많이 쓰이는 폰트 패밀리(`--font-family-base`), 자주 쓰이는 폰트 크기들(`--font-size-*`, 빈도 높은 걸 base로), 가장 흔한 line-height(`--line-height-base`), 자주 쓰이는 색상(`--color-*`). 이후 모든 컴포넌트는 이 변수만 참조한다.

회사 표준 브레이크포인트(태블릿 `max-width: 1295px`, 모바일 `max-width: 744px`)도 이 시점에 layout.css 상단에 주석으로 문서화해둔다: `/* 브레이크포인트: 태블릿 max-width 1295px, 모바일 max-width 744px (회사 표준, 프로젝트 전체 공통) */` — 실제 브레이크포인트 CSS 작성은 `pub-responsive`가 담당하지만, 토큰 문서화는 여기서 한다.

## 고정 규칙 (절대 어기지 않음)

1. **이미지/아이콘**:
   - **SVG(벡터)**: 실제 이미지 파일로 만들지 않고 `<svg>...</svg>`를 HTML 안에 인라인으로 삽입한다. `fill="currentColor"`로 색상을 CSS에서 제어할 수 있게 한다. 이건 규칙 7(인라인 스타일 금지) 대상이 아니다. **이 규칙은 페이지 안에 아이콘이 몇 개 있는지와 무관하게, 아이콘 하나하나에 개별적으로 적용된다.** 화살표, 플러스 버튼, 체크 아이콘처럼 단순한 개별 아이콘은 페이지 전체에 그런 아이콘이 수십 개 있어도 전부 다 인라인 SVG로 만든다 — "개수가 많으니 이번엔 이미지로 처리하자"고 판단하지 않는다.
   - **아이콘을 임의로 지어내지 않는다(필수)**: 피그마 참고 코드에서 아이콘/그래픽 요소가 `<svg>`+`<path>` 형태가 아니라 `<img src={...}>`(에셋 URL)로 내려오면, 그건 피그마가 그 요소를 이미지 에셋으로 제공한 것이다. "이런 모양이겠지"라고 비슷해 보이는 아이콘을 직접 지어내서 대체하지 않는다. 실제 에셋을 다운로드해서 확인한다.
   - **다운로드한 에셋이 SVG 파일이면, `<img src="...svg">`로 참조하지 않고 그 파일 내용을 열어서 인라인으로 옮긴다(필수, 실제 사고 사례 있음).** "아이콘을 임의로 지어내지 않는다"는 규칙과 "SVG는 항상 인라인"이라는 규칙이 부딪히는 지점이다 — 다운로드한 게 SVG(텍스트/XML)라면 그 내용을 읽어서 `<svg>...</svg>`로 그대로 인라인 삽입하고, 다운로드했던 파일 자체는 최종 결과물에 남기지 않는다. `<img>` + 파일 저장 방식은 **진짜 래스터 이미지(PNG/JPG)일 때만** 쓴다. "실제 에셋을 확인해야 한다"는 게 "파일로 남겨서 img로 참조해도 된다"는 뜻이 아니다.
   - **이전에 다른 페이지에서 썼던 아이콘 path를 재사용하지 않는다(필수).** "이거 예전에 만든 아이콘이랑 비슷해 보이니까 그 path 그대로 쓰면 되겠지"처럼, 지금 조회하지 않고 과거 다른 프레임에서 쓴 SVG path를 기억해서 재활용하지 않는다 — 다른 프레임이면 겉보기에 비슷해도 실제 디자인이 다를 수 있다. 아이콘마다 이번에 조회한 이번 프레임의 실제 데이터에서 나온 path만 쓴다.
   - **반복 SVG의 `id` 충돌 방지(필수)**: `<defs>`의 `linearGradient`/`mask`/`clipPath`/`filter` id가 같은 페이지에서 여러 번 반복되면 두 번째부터 깨진다. 인스턴스마다 id를 고유하게(`-1`, `-2` 등) 만든다.
   - **래스터 이미지**: 추출 가능하면 `files/{영역}/images/common/파일명`으로 저장. 불가능하면 임의로 만들지 않고 크기만 잡은 빈 영역(전용 클래스로 크기 정의)으로 처리.
   - SVG인지 래스터인지 애매하면 임의로 정하지 말고 물어본다.
   - **크롭 정확도**: 부모 프레임/여백까지 통째로 잘라내지 않고, 실제 이미지 경계와 일치하는 가장 안쪽 노드만 추출한다.
   - **크롭 검증 및 재크롭**: 다운로드 파일의 실제 픽셀 크기와 피그마 레이아웃 표시 크기를 비교, 다르면 ImageMagick/Pillow 등으로 재크롭. 좌표 판단이 애매하면 전/후 비교 이미지로 확인받는다.
   - **크기 보정**: `<img>`에 `object-fit: cover; object-position: center;` 기본 적용.
   - **`<img>` 태그에 `width`/`height` 속성을 넣지 않는다(필수).** 크기는 CSS에서 클래스로 지정한다 — HTML 속성으로 박아두면 반응형에서 크기가 바뀌어야 할 때 CSS 값과 속성값이 서로 다르게 남아 혼란스럽고, 실제로 CSS가 이겨서 속성값은 의미 없어지는데도 코드에 남아있어 가독성만 떨어뜨린다. 이미지 크기는 전부 CSS(`width`, `height`, 또는 `aspect-ratio`)로 관리한다.
   - **img/svg 크기를 여러 개를 묶는 공통(범용) 선택자로 한 번에 지정하지 않는다(필수).** `img { width: 100px; }`나 `svg { width: 24px; height: 24px; }`처럼 태그 자체를 범용으로 선택해서 페이지 안의 서로 다른 여러 이미지/아이콘에 한꺼번에 같은 크기를 적용하지 않는다 — 이러면 그 중 하나만 반응형에서 다르게 조정하고 싶어도 공통 규칙을 건드리면 나머지 전부가 같이 바뀌어버려서 개별 수정이 불가능해진다. **이미지/아이콘 인스턴스마다 각자의 전용 클래스**(`.main-hero__badge`, `.notice-panel__day-dot` 등)를 만들어서 그 클래스에 크기를 지정한다. 여러 이미지가 우연히 같은 크기를 공유하더라도, 각자 나중에 독립적으로 조정될 가능성이 있으면 전용 클래스로 분리해둔다.
   - **확장자-내용 일치 검증(필수)**: 저장 시 `file` 명령어 등으로 확장자와 실제 포맷이 맞는지 확인, 불일치 시 바로잡는다.
2. **폼/인터랙션 요소는 실제 시맨틱 HTML로 만든다**: 드롭다운은 `<select>`, 체크박스/라디오는 `<input type="checkbox/radio">`, 토글은 `<input type="checkbox" role="switch">` + `checked`/`aria-checked`. div/span으로 흉내만 내는 것 금지.
   - **접근성**: `accessibility-prompt-rules` 스킬이 있으면 WCAG 2.1 AA 기준도 같이 적용.
   - **JS 없이 작동 안 하는 요소**(탭/아코디언/모달)는 발견 시 조용히 넘어가지 않고 "마크업만 있고 JS 필요, 만들어드릴까요?"를 보고에 명시.
3. **hover/focus**: 피그마에 실제로 표현된 상태만 구현, 추측 금지.
4. **클래스 재사용**: 기존 design.css 먼저 확인, 비슷한 게 있으면 재사용, 완전히 새로울 때만 신규 클래스. 애매하면 규칙 12.
5. **클래스 네이밍**: kebab-case + BEM, 블록명 앞에 컴포넌트/페이지 접두사 필수(`.tag`, `.input` 같은 일반명 금지). 기존 무접두사 클래스 전체 리네이밍은 임의로 안 하고 규칙 12에 따라 확인. **아이콘 버튼**은 매번 `display:flex;align-items:center;justify-content:center;` + svg `width`/`height` 명시.
   - **메인 페이지와 서브 페이지의 구조가 다르면 클래스도 명확히 구분한다.** 메인 전용 컴포넌트와 서브 전용 컴포넌트를 같은 클래스명으로 섞어 쓰지 않는다 — 접두사나 블록명 자체를 다르게 해서(`main-hero` vs `sub-visual` 등) 나중에 어느 페이지에서 쓰는 클래스인지 헷갈리지 않게 한다.
   - **GNB처럼 메인/서브 공통으로 재사용하는 요소도, 실제로 메인과 서브에서 색상 등 스타일이 다를 수 있다는 걸 염두에 둔다.** "공통 요소니까 완전히 똑같겠지"로 넘겨짚지 않고, 서브 페이지 작업 시 GNB를 재사용할 때 실제로 그 페이지의 GNB가 메인과 동일한 색상/스타일인지 참고 코드로 확인한다. 다르면 페이지별 변형 클래스(`.gnb--sub` 등)로 구분해서 처리한다.
6. **색상/폰트/사이즈**: 하드코딩 금지, `var(--...)`만 참조, 없으면 layout.css에 추가.
7. **스타일 작성 위치**: `layout.css`/`design.css`에만 작성, HTML에 `<style>`/`style=""` 절대 금지.
7-1. **HTML 코드는 읽기 편하게 정리한다.** 태그 하나의 속성을 억지로 한 줄에 하나씩 쪼개서 세로로 길게 늘어놓지 않는다 — `class`, `id`, `aria-*`, `src`, `alt` 등 짧은 속성들은 한 태그 안에 자연스럽게 한 줄로 쓴다(전체 줄이 너무 길어질 때만 줄바꿈). 들여쓰기는 부모-자식 구조를 따라 일관되게 한다.
8. **리셋 범위 검증**: `<p>`,`h1~h6`,`ul/ol/li`,`button`,`fieldset/legend`,`input/select/textarea`,`figure` 등 브라우저 기본 여백/테두리가 layout.css 리셋에 커버되는지 확인, 없으면 추가.
   - **`box-sizing: border-box` 전역 적용(필수)**: `*, *::before, *::after { box-sizing: border-box; }`가 layout.css에 있는지 확인, 없으면 추가.
   - **`html, body`에 `overflow-x: hidden` 안전장치를 필수로 둔다.** 개별 요소의 고정폭/좌표 문제를 하나하나 찾아 고치는 것과 별개로, `layout.css`에 `html, body { overflow-x: hidden; }`이 있는지 확인하고 없으면 추가한다. 이건 원인을 안 찾아도 되는 핑계가 아니라 **마지막 안전망**이다 — 어딘가 놓친 요소가 있어도 페이지 전체 가로 스크롤로 번지지 않고 그 안에서 잘리게 막아준다. 이 안전장치가 있어도 실제 원인이 되는 요소(고정폭, 절대좌표 등)는 위 규칙대로 그대로 찾아서 고친다 — 안전장치는 사고를 완화할 뿐 원인 수정을 대체하지 않는다.
9. **웹표준 준수**: `zoom` 등 비표준/레거시 속성, 벤더 핵 금지. Flexbox/Grid/`%`/`aspect-ratio`/`clamp()` 등 표준 CSS로 구현.
10. **긴 텍스트/실제 데이터 대비**: 고정 너비/줄수 텍스트 영역엔 오버플로우 처리 기본 적용 — 한 줄은 `overflow:hidden;text-overflow:ellipsis;white-space:nowrap;`, 여러 줄은 `-webkit-line-clamp:N` 방식. 배지/태그처럼 짧고 고정된 값은 생략 가능, 애매하면 규칙 12.
11. **요청 범위를 벗어난 콘텐츠 추가 금지**: 결과물의 모든 섹션은 (a) 이번 프레임 내용이거나 (b) 정당하게 재사용한 GNB/LNB/헤더/푸터, 둘 중 하나로 설명돼야 한다.
12. **애매한 판단**: 재사용 여부, 정보 부족, 그 밖의 임의 결정 상황은 반드시 먼저 사용자에게 물어본다.

## 생성 후 자기 점검 (사용자에게 보고하기 전에)

같은 세션에서 [자기 점검 체크리스트]를 빠르게 확인하는 것으로 평소엔 충분하다. `figma-review-agent`(Opus, 독립 컨텍스트)는 아래 "픽셀 단위 검증 루프"에서 정한 경우에만 호출한다.

- `figma-review-agent`는 플러그인에 이미 포함되어 배포된다(`pub/agents/figma-review-agent.md`). 매번 있는지 확인하거나 새로 만들려 하지 않는다 — 필요할 때 Task 도구로 이름만 호출.

## 픽셀 단위 검증 루프 (기본은 가볍게, 필요할 때만 정밀하게)

기본은 매 섹션마다 안 돌린다. 사용자의 명시적 요청 / 페이지 전체 최종 확정 시점 / 이미 차이를 발견해 정확한 위치가 필요할 때만 돌린다.

**토큰 절약**: 피그마 재조회 안 함(생성 세션의 스크린샷/데이터 재사용), Opus는 기본 미사용(반복 실패 시에만), 반복 최대 1~2회, 기준치 3%.

`pub/scripts/capture.js`/`diff.js`가 있으면: 캡처 → 피그마 원본과 비교(기준치 3%) → FAIL이면 diff 이미지 좌표로 구체 수정 후 최대 1~2회 재시도 → 그래도 안 되면 남은 차이를 사용자에게 보고. 스크립트가 없으면 체크리스트만으로 진행하되 그 사실을 알린다.

## 자기 점검 체크리스트

그룹별로 한 번에 훑는다.

1. **시각적 비교**: 생성 결과와 (3번에서 이미 받은, 재조회 안 하는) 스크린샷을 비교, 다른 부분은 위치/정도로 구체적으로 짚는다. 없어진 시각 속성 있으면 부모 노드 누락 의심. 100% 재현 어려운 부분은 근사치임을 밝힌다. 피그마에서 같은 줄에 있던 요소가 결과물에서 분리돼 있으면 그룹핑 구조를 다시 대조해서 고친다.
2. **시맨틱/기능 + 코드 위생**: select/checkbox/radio/toggle 시맨틱 여부, 인라인 style/`<style>` 없음, `zoom` 등 비표준 없음, 이미지 확장자-내용 일치, 반복 SVG id 고유성을 한 번에 훑는다.
3. **레이아웃/범위 무결성**: 다컬럼 카드 높이 합 일치(피그마 고정 높이 반영), `box-sizing: border-box` 리셋 유무로 인한 페이지 전체 가로 스크롤 없음, 모든 섹션이 (a) 이번 프레임 (b) 정당한 GNB/LNB/헤더/푸터 재사용 중 하나로 설명되는지(규칙 11) 확인.

문제 발견 시 보고 전에 고친다. 애매하면 규칙 12.

## 보고 후 다음 진행 확인 (필수)

**이 질문은 이번 작업이 완전히 끝났을 때만 나온다.** 반응형 작업이면 웹/태블릿 완료 시점엔 나오지 않고, 모바일까지 끝나고 `pub-responsive` 최종 보고 후에만 나온다.

보고 후 그냥 끝내지 않는다. `AskUserQuestion`으로 아래 문구를 그대로 사용해서 물어본다:

- 질문: "다음으로 무엇을 할까요?"
- 선택지 1: "다음 프레임 이어서 만들기" / "다음 프레임/섹션을 이어서 생성합니다" (후보 있으면 이름도 제시)
- 선택지 2: "수정할 부분 직접 알려주기" / "어떤 부분이 잘못됐는지 구체적으로 말씀해주세요"
- 선택지 3: "이전 단계로 돌아가기" / "이미 만든 부분(예: 웹 버전)으로 돌아가서 이어서 작업합니다"
- 선택지 4: "오늘 작업 마무리" / "여기서 종료합니다"

답 없이는 다음 프레임을 알아서 진행하지 않는다.
