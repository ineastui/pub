# 피그마 → 퍼블리싱 코드 생성 (웹/기본 버전)

> 스킬 버전: 5.13.0 — 이 줄의 버전 번호가 최신인지 확인하세요. 다른 대화창/세션에서 작업한 버전과 다르면 아직 동기화가 안 된 것입니다.

## 최우선 원칙: 유추하지 않는다, 확인한다

**이 스킬 전체를 관통하는 단 하나의 원칙이다.** 색상, 크기, 위치, 회전, 배경, 정렬, 여백, 반응형 여부 등 **어떤 값이든** "이 정도면 맞겠지", "저쪽이 이러니 이쪽도 비슷하겠지", "보통 이런 건 이렇게 하니까"로 채워 넣지 않는다. 아래는 실제로 이런 유추 때문에 생긴 사고들이다 — 전부 "직접 확인했으면 안 생겼을" 문제다:

- 배경이 있는 카드 옆에 비슷한 카드를 만들면서 배경을 빠뜨림
- 왼쪽 버튼을 회전시켜 오른쪽 버튼도 그럴 거라 가정하고 위치/회전을 안 맞춰봄
- 아이콘 크기를 어림잡아 140px처럼 대충 채워 넣음
- 여백이 있어야 할 것 같아서 근거 없이 padding을 추가하거나, 반대로 없앰
- 이전에 만든 페이지의 아이콘과 비슷해 보여서 그 코드를 그대로 재사용

**이 스킬의 모든 세부 규칙(속성 1:1 보존, 노드 완전성 확인, 치수표 작성 등)은 결국 이 원칙 하나를 구현하는 방법일 뿐이다.** 값 하나라도 확신이 안 서면, 진행하지 말고 그 부분을 실제로 다시 조회해서 확인한다.

**이 스킬은 웹(기본) 버전을 만드는 것까지만 담당한다. 태블릿/모바일 반응형은 `pub-responsive` 절차로 넘긴다.** 작업 시작 시 1-4에서 일반/반응형을 먼저 명확히 구분하고, 반응형이면 사용자가 별도 명령을 입력할 필요 없이 이 흐름 그대로 `pub-responsive`의 절차로 자동 이어간다.

## 사용자에게 질문할 때 (전체 공통)

이 스킬에서 나오는 모든 선택형 질문(영역 선택, 새/기존 페이지 선택, 파일 선택 등)은 **반드시 `AskUserQuestion` 도구를 사용**한다. 그냥 텍스트로 나열만 하고 타이핑으로 답하게 하지 않는다.

- **질문 문구와 선택지 라벨은 한글로 작성한다.** `main.html`, `sub.html` 같은 실제 파일명 자체는 영문 그대로 두되, 그 옆에 한글 설명을 병기한다.
- `AskUserQuestion`의 "Type something." / "Chat about this" 같은 고정 UI 문구는 도구 자체의 고정 표시라 스킬로는 바꿀 수 없다.

## 작업 전제

- 이 스킬은 반드시 실제 프로젝트 폴더 안에서 실행 중인 Claude Code 세션에서 사용한다.
- **작업 폴더 안에 영역이 명확할 때만 그 폴더가 곧 "영역"이다.** 상위 폴더에 web1/web2/bcnimda처럼 여러 영역이 함께 있으면 자동으로 정하지 말고 반드시 사용자에게 먼저 물어본다.
- layout.css, design.css는 실제 파일이다. git으로 커밋되면 다른 퍼블리셔와 자연스럽게 공유된다.

## 작업 절차

0. **버전 확인 — 매 실행의 첫 단계. 건너뛰지 않는다.**

   업데이트 여부는 `plugin.json`의 `version`으로 판단한다(플러그인 업데이트가 이 값을 기준으로 내려오기 때문). 본문 맨 위의 "스킬 버전"은 표시용으로 같이 보여준다.
   - 설치된 버전: `cat "$CLAUDE_PLUGIN_ROOT/plugin.json"` 의 `version`
   - 최신 버전: `curl -s --max-time 3 https://raw.githubusercontent.com/ineastui/pub/main/pub/plugin.json` 의 `version`
     (curl이 없거나 실패하면 같은 주소를 `WebFetch`로 한 번만 시도한다)

   결과에 따라 이렇게 한다.
   - **같으면** — 이 한 줄만 출력하고 곧바로 1번으로 넘어간다. 더 설명하지 않는다.
     ```
     pub 스킬 v{본문 버전} · 플러그인 v{설치된 버전} · 최신
     ```
   - **다르면** — 아래를 출력하고, `AskUserQuestion`으로 "지금 업데이트 받기" / "그냥 이 버전으로 진행"을 묻는다.
     ```
     ⚠ pub 업데이트가 있습니다
        설치됨: 플러그인 v{설치된 버전}  →  최신: 플러그인 v{깃허브 버전}
     ```

     - **"지금 업데이트 받기"를 고르면**: 사용자에게 명령어를 시키지 말고 **직접** `claude plugin update pub` 을 실행한다. 성공하면 아래를 출력하고 **거기서 작업을 멈춘다** — 재시작 전에는 옛날 스킬이 계속 돌기 때문에 이어서 진행하면 의미가 없다.
       ```
       ✓ 새 버전을 받았습니다.
         Claude Code를 껐다 켠 뒤 /pub 을 다시 실행해주세요.
       ```
       실패하면 오류 내용을 그대로 보여주고, `claude plugin marketplace update publishing-tools` 를 먼저 실행한 뒤 한 번만 다시 시도한다. 그래도 안 되면 오류를 보고하고 "그냥 이 버전으로 진행"할지 묻는다.
     - **"그냥 이 버전으로 진행"을 고르면**: 아무 말 없이 1번으로 넘어간다.
   - **확인 실패**(네트워크 차단 등) — 이 한 줄만 출력하고 그냥 진행한다. 확인이 안 된다고 작업을 막지 않는다.
     ```
     pub 스킬 v{본문 버전} · 플러그인 v{설치된 버전} · 최신 버전 확인 못 함
     ```

1. **아래 순서를 매번 무조건, 하나씩 순서대로 진행한다.**

   **1-1. 영역 확인**
   - 항상 지금 Claude Code 세션이 실행된 현재 폴더를 기준으로 진행한다. "실제 프로젝트 폴더 경로를 알려달라"거나 다른 폴더로 옮겨서 작업하자는 식으로 되묻지 않는다.
   - 현재 폴더 또는 `inc/` 아래에 이미 만들어진 영역 폴더가 있으면, 그 이름을 선택지로 제시하고 "기타(직접 입력)"도 함께 제시한다.
   - 영역 폴더가 하나도 없어도 마찬가지로 현재 폴더에서 바로 물어본다.
   - 지금 실행 위치가 이미 특정 영역 폴더 안이라 다른 후보가 아예 없을 때만 예외적으로 이 단계를 묻지 않는다.

   **1-2. 새 페이지인지 기존 페이지인지 확인**
   - `html/{영역}/` 폴더 안의 파일 목록을 실제로 조회한다. 폴더가 없거나 비어 있으면 새 페이지로 진행. 파일이 하나 이상 있으면 반드시 물어본다: "새 페이지를 만들까요, 아니면 기존 페이지에 이어서 작업할까요?"

   **1-3. (기존 페이지인 경우) 대상 파일 선택**
   - 파일 목록을 `AskUserQuestion`으로 제시해서 화살표 키로 고를 수 있게 한다. 10개 이상이면 이름 검색으로 먼저 좁힌다.

   **1-4. 일반/반응형 구분 + 피그마 프레임 지정 확인 + (새 페이지인 경우) 파일명 자동 결정**
   - **가장 먼저 `AskUserQuestion`으로 명확히 구분해서 물어본다**: "이번 작업은 일반(웹 버전만)인가요, 반응형(웹+태블릿+모바일)인가요?" — 사용자의 원래 요청에 "반응형", "태블릿", "모바일" 같은 말이 이미 있었다면 그 답이 명확하니 다시 묻지 않고 바로 그쪽으로 진행한다.
     - **일반이면**: 아래 순서대로 이 스킬(`/pub`) 안에서 계속 진행한다. 웹 피그마 링크를 물어본다('Copy link to selection'으로 복사한 node-id 포함 링크).
     - **반응형이면**: 사용자에게 별도 명령을 다시 입력하라고 시키지 않는다. **이 흐름 그대로, `pub-responsive` 스킬(`${CLAUDE_PLUGIN_ROOT}/skills/pub-responsive/SKILL.md`)의 절차를 이어서 그대로 따른다** — 사용자 입장에서는 `/pub` 한 번 실행한 것으로 끝까지 이어지는 것처럼 보여야 한다. 다만 웹 버전 생성(1~6번, 고정 규칙)까지는 이 스킬대로 하고, 그 다음 반응형 단계(웹→태블릿→모바일 순차, 완전 대조, 커버리지 표 등)부터는 `pub-responsive`에 정의된 절차와 형식을 그대로 적용한다. 두 스킬의 규칙을 다르게 섞어 쓰지 않는다 — 반응형 부분은 전적으로 `pub-responsive`의 규칙을 따른다.
   - **같은 프레임을 다시 요청받으면 기본적으로 "재검증 후 수정" 모드로 동작한다.** 기존 구현이 있으면, **같은 세션의 자기 점검이 아니라 `figma-review-agent`(Opus, 독립 컨텍스트)를 Task 도구로 호출해서 재검증한다.** 방금 만든 걸 만든 사람이 다시 봐서 "문제없다"고 넘기는 걸 막기 위해서다. 검증에서 문제가 나오면 그 부분만 고친다. "처음부터 다시 만들어줘"일 때만 완전 재생성.
   - **새 페이지인 경우, 파일명을 따로 물어보지 않고 프레임 이름 기반으로 자동 결정한다.**
     - 메인/대표 페이지는 `index.html`이 아니라 `main.html`.
     - `sub.html`, `list.html`, `detail.html`처럼 구분 안 되는 이름 금지 — 프레임 이름 반영해서 구체적으로.
     - 겹치면 더 구체화. 자동 결정 후 "이 이름으로 만들었어요, 마음에 안 들면 말씀해주세요" 정도로만 안내.

   **공통 규칙**
   - **한 번 확인된 항목은 다시 묻지 않는다.** 단, 이 범위는 지금 실행 중인 `/pub` 한 번의 호출 안에서만이다 — `/pub`을 다시 실행하면 매번 새 작업으로 취급하고 1-1부터 다시 시작한다.
   - 확인 완료되면 `html/{영역}/`, `files/{영역}/images/common/` 구조가 없을 경우 생성한다. **CSS 폴더(`inc/{영역}/css/`)는 2번에서 통합형으로 판별된 경우에만 만든다** — 분산형이면 기존 배치를 그대로 쓰고 새 폴더를 만들지 않는다. 별도로 안 물어봐도 된다.
   - **작업 도중 영역 전환** 요청이 오면 즉시 전환하고 1-2부터 다시 진행, 이전 영역과 안 섞이게 한다.

2. **CSS 구조를 먼저 판별한다(필수). 구조를 넘겨짚고 시작하면 엉뚱한 파일에 스타일을 쓴다.**
   프로젝트마다 CSS 배치가 다르다. 이 스킬의 기본형(`inc/{영역}/css/`)이 아닌 프로젝트도 있으므로, 매번 실제 폴더를 확인해서 어느 쪽인지 정한다.
   ```
   find . -name "*.css" -not -path "*/node_modules/*" | head -40
   ```
   판단은 아래 순서대로 기계적으로 한다. **사용자에게 어느 구조인지 묻지 않는다** — 물어봐야 알 수 있는 게 아니라, 파일을 보면 확정되는 사실이다.

   1. **기존 페이지가 있으면 그 HTML의 `<link>` 목록이 정답이다.** 추측할 필요 없이 그 페이지가 실제로 무엇을 불러오는지 그대로 나온다. 같은 영역/폴더의 아무 페이지나 하나 열어서 확인한다.
      ```
      grep -n 'stylesheet' html/{영역}/*.html   # 또는 해당 프로젝트의 HTML 경로
      ```
      - 링크가 `inc/*/css/layout.css` + `design.css`를 가리키면 → **통합형**
      - 링크가 각 페이지/섹션 폴더 안의 CSS를 가리키면 → **분산형**
      - **이번에 만들 페이지도 같은 폴더의 기존 페이지와 똑같은 `<link>` 구성을 쓴다.** 이게 스타일이 실제로 적용되는지를 좌우한다.
   2. **기존 페이지가 하나도 없으면**(빈 프로젝트 첫 실행) `inc/*/css/design.css`의 존재 여부로 정한다. 있으면 통합형, 없으면 통합형 구조를 새로 만든다(기본형).

   - **통합형**: 기존대로 진행한다. design.css가 크면 관련 키워드로 grep해서 관련 블록만 확인한다(300줄 이하이거나 첫 실행/대개편일 땐 전체 확인). 파일이 없으면 새로 만든다.
   - **분산형**: 아래 [분산형 CSS 프로젝트]를 따른다.
   - 한 번 정하면 이번 `/pub` 실행 내내 그 구조로 일관되게 간다.

   ### 분산형 CSS 프로젝트

   - **기존 배치 규칙을 따르고, 파일을 새로 만들거나 한곳으로 모으지 않는다.** "정리하는 김에 통합하자"는 판단을 임의로 하지 않는다 — 다른 페이지가 그 파일들을 참조하고 있다. 구조를 바꿔야 할 것 같으면 규칙 12로 물어본다.
   - **어느 섹션의 스타일을 어느 파일에 쓸지, CSS 작성 전에 노드 인벤토리 표의 `CSS 파일` 열에 미리 정해둔다.** 작성하면서 그때그때 정하면 같은 페이지 스타일이 여러 파일에 흩어진다.
   - **`:root` 토큰이 정의된 파일이 이번 페이지의 `<link>`에 실제로 들어 있는지 확인한 뒤에 `var(--...)`를 쓴다(필수).** 분산형은 토큰 파일이 일부 페이지에만 연결돼 있는 경우가 있다. 로드 안 되는데 `var()`를 쓰면 값이 통째로 비어서 스타일이 사라진다 — 이때는 임의로 하드코딩하지 말고 규칙 12로 물어본다(토큰 파일을 링크에 추가할지, 이 파일에 토큰을 따로 둘지).
   - **자기 점검 grep은 이번에 손댄 CSS 파일 전부에 돌린다.** 한 파일만 확인하고 나머지는 괜찮겠지로 넘기지 않는다.
   - 완료 보고에서 **파일별로 나눠서** 무엇을 넣었는지 적는다.
3. 연결된 Figma 도구로 `$ARGUMENTS`로 받은 링크의 프레임을 분석한다.
   - **공통 레이아웃(GNB/LNB/헤더/푸터) — 서브 페이지에만 적용**: GNB/LNB/헤더/푸터가 포함돼 있으면 다시 분석해서 새로 만들지 않는다. 메인 페이지(`main.html`)는 이 규칙 예외 — 항상 피그마 메인 프레임 기준으로 그대로 만든다. 재사용 범위는 `<header>`/`<nav>`/`<footer>` 태그나 `gnb`/`lnb`/`header`/`footer`/`nav` 클래스로 식별되는 요소로 엄격히 한정하고, 다른 콘텐츠 섹션을 같이 끌어오지 않는다. 기존 서브 페이지에서 grep으로 그 부분만 찾아 복사, 없으면 이번에 만들고 "기준 버전"이라고 안내. **복사해 온 공통 레이아웃은 마크업을 그대로 유지한다** — 규칙 2의 시맨틱 규칙(`<ul>/<li>` 등)을 근거로 임의로 다시 짜지 않는다(이 부분에 한해 복사가 우선). 구조를 고쳐야 한다고 판단되면 규칙 12로 물어본다. 디자인이 달라 보이면 임의로 새로 만들지 말고 확인.
   - **노드 완전성 확인(필수)**: 스크린샷엔 보이는데 참고 코드에 없는 시각 속성(테두리/배경/그림자)이 있으면 부모 노드 누락을 의심하고 부모까지 포함해서 다시 조회한다.
   - **속성 1:1 보존(필수)**: border, background, border-radius, box-shadow, 정확한 색상/변수, padding/gap 수치, 그리고 **타이포 속성(`font-size`, `font-weight`, `line-height`, `letter-spacing`, `text-align`)**을 하나도 빠짐없이 그대로 옮긴다. **`letter-spacing`을 특히 놓치지 않는다** — 한글 디자인은 `-0.02em` 같은 음수 자간을 거의 항상 쓰는데, 이게 빠지면 글자 폭과 줄바꿈 위치가 눈에 띄게 달라진다("뭔가 다른데 어디가 다른지 모르겠는" 차이의 흔한 원인). `font-weight`도 300/400/500/700을 눈대중으로 뭉뚱그리지 않고 참고 코드 값 그대로 쓴다. 프레임워크 문법만 걷어내고 구조/수치는 유지. **`border-radius`가 네 모서리 전부가 아니라 특정 모서리 하나(예: `rounded-bl-[280px]` = 왼쪽 아래만)만 지정된 경우를 놓치지 않는다** — 참고 코드에 `rounded-tl/tr/bl/br` 같은 개별 모서리 클래스가 있으면 `border-top-left-radius` 등 해당 모서리 속성만 정확히 옮긴다.
   - **불투명도·그라디언트·그림자·블러는 피그마 값과 CSS 속성이 1:1이 아니다(필수).**
     - **레이어 불투명도와 색상 알파를 구분한다.** 레이어 자체 opacity 40%는 `opacity: .4`(자식 텍스트까지 흐려짐), 채우기 색 알파 40%는 `rgba(...,.4)`(자식은 선명). 바꿔 쓰면 위에 얹힌 글자가 흐려지거나 배경이 진해진다.
     - **그라디언트 방향을 눈대중으로 정하지 않는다.** 피그마는 각도가 아니라 핸들 좌표로 준다 — 시작·끝 좌표로 각도를 정하고(위→아래 `180deg`, 왼→오른쪽 `90deg`), 정지점 위치 %와 개수, `linear`/`radial` 구분까지 전부 옮긴다.
     - **그림자는 x, y, blur, spread, 색상 다섯을 다 옮긴다.** spread가 0이 아닌데 빠뜨리면 크기가 눈에 띄게 달라진다. 안쪽 그림자는 `inset`, 여러 겹이면 쉼표로 전부.
     - **블러는 대상을 구분한다.** 레이어 블러는 `filter: blur()`(그 요소가 흐려짐), 배경 블러는 `backdrop-filter: blur()`(뒤가 흐려짐, 배경색에 알파 필요).
   - **텍스트 1:1 보존(필수) — 한 글자도 바꾸지 않는다.** 피그마에 적힌 문구를 그대로 옮긴다. 띄어쓰기, 문장부호, 대소문자, 조사, 숫자 표기(`1,000` vs `1000`), 단위 붙임(`10 %` vs `10%`)까지 전부 원문 그대로다. 오탈자처럼 보이거나 문장이 어색해도 **임의로 고치지 않는다** — 고쳐야 할 것 같으면 규칙 12에 따라 먼저 물어본다(디자인 확정 문구인 경우가 많다).
     - **줄바꿈 위치도 디자인의 일부다(필수).** 피그마에서 한 텍스트가 두 줄로 보일 때, 그게 (a) 폭이 좁아 자동으로 넘어간 것인지 (b) 디자이너가 의도적으로 개행을 넣은 것인지 구분한다. 판단 근거는 눈대중이 아니라 **텍스트 노드의 실제 폭과 내용**이다 — 노드 폭이 넉넉한데도 줄이 나뉘어 있으면 강제 개행이다. 강제 개행이면 그 위치에 `<br>`를 넣어 똑같이 재현하고, 자동 줄바꿈이면 `<br>` 없이 CSS 폭에 맡긴다. 한글은 어절 단위 개행 위치가 디자인 인상을 크게 좌우하므로 임의로 옮기지 않는다.
     - **더미/샘플 텍스트를 만들어 채우지 않는다.** 피그마에 실제 문구가 없어서 비어 보이면, 그럴듯한 문장을 지어내지 말고 규칙 12로 물어본다.
   - **고정 폭(px)과 유동 분할(`flex:1 0 0`)을 서로 바꿔치기하지 않는다(필수).** 둘 다 "형제 요소들이 나란히 배치된다"는 점에서 겉보기엔 비슷해 보이지만 실제 동작은 다르다 — 참고 코드가 고정 `width: 597px` 같은 값이면 그대로 고정폭으로 옮기고, 참고 코드가 `flex: 1 0 0`(균등 분할)이면 그대로 flex로 옮긴다. "이 정도면 비슷하게 나오겠지"로 임의 대체하지 않는다(실제 사례: 고정 597px여야 하는 카드 두 개를 `flex:1 0 0`으로 잘못 바꿔서, 콘텐츠 양에 따라 카드 크기가 원본과 다르게 나온 사고가 있었다).
   - **부모-자식 그룹핑 구조 보존(필수)**: 참고 코드에서 형제로 같이 있는 요소는 구현에서도 반드시 같은 부모 안에 형제로 둔다. 값은 맞아도 그룹 구조가 달라지면 레이아웃이 어긋난다.
   - **`align-items`를 빠뜨리면 자식이 원치 않게 늘어난다(필수 확인).** 참고 코드의 `flex` 부모에 `items-start`/`items-center`/`items-end`가 있는데 빠뜨리면 기본값(`stretch`)이 적용돼서 자식이 부모 크기만큼 늘어난다. 자식 크기가 이상하면 부모의 `align-items`부터 확인한다.
   - **`flex-direction: column`을 레이아웃 기본값처럼 습관적으로 쓰지 않는다.** 세로로 쌓인 배치를 볼 때마다 일단 `display:flex; flex-direction:column;`부터 쓰고 보는 습관이 있으면, `align-items`를 빠뜨려서 자식들이 전부 `width: 100%`처럼 늘어나는 사고가 반복된다. `flex-direction: column`을 쓸 때는 **그때마다 반드시** 참고 코드의 `align-items` 값을 같이 확인해서 명시한다 — "일단 column으로 잡고 나중에 정렬 확인"이 아니라 두 속성을 항상 같이 세트로 정한다.
   - **이전/다음, 좌/우처럼 짝을 이루는 요소가 서로 완전한 대칭(거울 관계)일 거라고 가정하지 않는다(필수).** 같은 아이콘을 재사용하면서 한쪽만 `rotate`/`scaleX(-1)` 등으로 반전시키는 패턴이 흔한데, 이때 "왼쪽이 이러니 오른쪽은 그 반대겠지"로 유추해서 만들지 않는다. 위치(순서, `left`/`right`), 회전 값, 아이콘 방향을 **양쪽 다 참고 코드에서 각각 직접 확인**한다 — 실제로 위치나 회전이 예상과 다르게 디자인된 경우가 있었다.
   - **레이어 이름이 아니라 실제 좌표(x/y)로 좌우/위치를 판단한다(필수, 실제 사고 사례 있음).** 피그마 레이어 이름이 "Left"/"Right", "prev"/"next"처럼 방향을 나타내도, 그 이름이 실제 좌표와 다를 수 있다(디자이너가 이름을 안 맞춰뒀거나 나중에 위치만 바꾼 경우) — 실제 사례로 "Right navigation arrow"라는 이름의 레이어가 `x=0`(왼쪽)에, "Left navigation arrow"가 `x=1324`(오른쪽)에 있던 적이 있었다. 이름만 보고 배치하면 좌우가 뒤바뀐다. `get_metadata`나 `get_design_context`로 받은 **실제 x좌표를 비교해서** 어느 게 왼쪽/오른쪽인지 판단하고, 이름은 클래스명 짓는 데만 참고한다(위치 판단 근거로 쓰지 않는다).
   - **정확한 값은 추측하지 않고 변수 정의를 조회**: 애매한 색상/이펙트는 `Figma:get_variable_defs`로 확인, 눈대중 금지.
   - **분석과 같은 호출에서 그 프레임의 스크린샷을 한 번 받아 세션에 남겨둔다(필수).** 노드 완전성 확인과 자기 점검의 시각적 비교가 전부 이 스크린샷을 재사용한다 — 점검 시점에 피그마를 다시 조회하지 않기 위해서다.
   - **토큰 최적화**: Figma 도구는 항상 특정 프레임/노드 하나만 지정해서 조회, 페이지/파일 전체 조회 금지.
   - **"프레임이 너무 커서 뼈대만 반환됐다"는 경고를 절대 무시하지 않는다(필수).** `get_design_context` 응답 끝에 "design was too large... sparse metadata response... call get_design_context on the IDs of the sublayers" 같은 경고가 붙어 있으면, 그 응답엔 색상/폰트/정확한 스타일 정보가 없고 **구조와 좌표만 있는 뼈대**라는 뜻이다. 이 상태로 절대 진행하지 않는다. 사용자가 준 링크가 페이지 전체 같은 거대한 프레임을 가리킬 때 이런 일이 생긴다.
     1. 받은 뼈대 메타데이터에서 실제로 필요한 부분에 해당하는 **하위 레이어 이름**(예: `_Top`, `_tit`, `_right`)을 찾는다. 사용자가 요청한 내용(스크린샷, 설명)과 이름이 맞는 하위 레이어를 고른다.
     2. 그 하위 레이어의 노드 ID로 `get_design_context`를 **다시** 호출한다.
     3. 그래도 또 "너무 크다"는 경고가 나오면, 한 단계 더 작은 하위 레이어로 쪼개서 반복한다 — 실제 스타일 정보가 담긴 응답을 받을 때까지 계속한다.
     4. 여러 하위 레이어로 나눠 조회했다면, 최종적으로 각 조회 결과를 조합해서 하나의 완성된 화면으로 만든다.
   - 이 확인 없이 뼈대 데이터만으로 만든 결과물은 색상/폰트/정확한 크기가 다 틀리고 반응형도 제대로 안 된다 — 이게 "피그마를 제대로 못 읽는다"는 문제의 흔한 원인이다.
   - **차트/그래프류, 그리고 복잡한 장식용 그래픽 다발은 예외 — 먼저 물어본다**: 방사형/도넛/막대/선 그래프뿐 아니라, 배너처럼 여러 개의 겹쳐진 순수 장식 SVG(리본, 별, 블롭 등)가 절대좌표로 다닥다닥 배치된 경우도 SVG 인라인을 자동 적용하지 않는다. **이 예외는 "그 그래픽 요소 하나(또는 한 묶음) 자체가 구조적으로 복잡한지"를 보는 것이지, "페이지 전체에 아이콘이 몇 개나 있는지"가 아니다.** 화살표/체크/플러스 같은 단순 개별 아이콘이 페이지에 아무리 많아도 이 예외 대상이 아니다 — 위 SVG 인라인 규칙 그대로 각각 인라인 처리한다. "SVG로 각각 코딩할지, 통 이미지로 대체할지" 먼저 확인한다. 나중에 슬라이드/캐러셀로 바뀔 예정이면 통 이미지를 강하게 권장한다. 이미지로 결정되면 개별 요소를 쪼개지 않고 통 이미지 하나로 처리(로고/텍스트/버튼 등 실제 콘텐츠는 기존 규칙대로 마크업).
4. 아래 [고정 규칙]에 따라 HTML을 생성한다.
   - **`<head>` 뼈대는 아래 형태로 고정한다(필수). 단 `<link>` 두 줄은 2번의 판별 결과를 따른다** — 통합형이면 아래 그대로, 분산형이면 같은 폴더 기존 페이지의 `<link>` 구성을 그대로 복사해 쓴다. `<!DOCTYPE>`·charset·viewport·`<title>`은 어느 구조에서든 아래대로 고정한다.
     ```html
     <!DOCTYPE html>
     <html lang="ko">
     <head>
     <meta charset="utf-8">
     <meta name="viewport" content="width=device-width, initial-scale=1">
     <title>{페이지명} | {사이트명}</title>
     <link rel="stylesheet" href="/inc/{영역}/css/layout.css">
     <link rel="stylesheet" href="/inc/{영역}/css/design.css">
     </head>
     ```
     - **CSS 링크 순서는 항상 `layout.css` → `design.css`로 고정한다.** 페이지마다 순서가 다르면 뒤에 오는 파일이 이기는 관계가 뒤집혀서, "이 페이지만 스타일이 다른데 원인을 모르겠는" 사고가 난다.
     - `<title>`은 피그마 프레임 이름/페이지 제목에서 가져온다. "무제" 같은 임시 문구를 남기지 않는다.
     - 같은 영역에 기존 페이지가 있으면 그 페이지의 `<head>`를 `grep`으로 그대로 가져와 맞춘다. 사이트명·favicon 경로를 모르면 지어내지 말고 규칙 12로 물어본다.
   - **`<body>` 바로 아래에는 전체를 감싸는 `<div id="wrapper">` 하나를 넣는다.** 헤더/GNB, 콘텐츠, 푸터가 `<body>` 밑에 각자 형제로 따로 떠 있지 않게, 이 셋을 전부 `#wrapper` 안에 넣는다. (예: `<body><div id="wrapper"><header>...</header><main>...</main><footer>...</footer></div></body>`)
   - **GNB/헤더/푸터처럼 문서 흐름을 따라야 하는 최상위 요소를 `position: absolute` + 고정 캔버스 폭으로 옮기지 않는다(필수).** 피그마 참고 코드가 이런 요소를 절대좌표로 내려주는 경우가 있는데, 그대로 옮기면 문서 흐름에서 완전히 빠지고 실제 뷰포트보다 좁은 화면(캔버스 폭과 뷰포트 폭이 다른 모든 경우)에서 어긋나거나 가로 스크롤이 생긴다. 이런 요소는 일반적인 문서 흐름(`position: static`, `width: 100%`)으로 만든다 — 실제로 겹쳐야 하는 특별한 이유(오버레이 등)가 명확할 때만 `position: absolute/fixed`를 쓴다.
   - **`position: absolute`를 쓰기로 했으면 기준 부모와 쌓임 순서를 같이 정한다(필수). 둘 중 하나만 하면 반드시 어긋난다.**
     - 자식에 `absolute`를 주는 순간, 좌표의 기준이 될 부모에 `position: relative`를 같이 넣는다. 어느 노드가 기준인지는 참고 코드에서 그 자식의 x/y가 어느 프레임 기준으로 적혀 있는지로 판단한다 — "어차피 위쪽 어딘가에 relative가 있겠지"로 넘기지 않는다. 기준 부모가 없으면 값은 1:1로 맞는데 위치만 완전히 틀리고, 원인 찾는 데 가장 오래 걸린다.
     - **겹치는 요소가 있으면 피그마 레이어 순서를 그대로 앞뒤 순서로 옮긴다.** 피그마 레이어 목록에서 나중에 그려지는 노드가 위에 보이는 요소다. HTML에서도 뒤에 오는 형제가 위에 오도록 마크업 순서를 맞추고, 순서만으로 안 되는 경우에만 `z-index`를 준다.
     - `z-index`에 999, 9999처럼 근거 없는 큰 값을 쓰지 않는다. 같은 부모 안에서는 1, 2, 3처럼 작은 값으로 겹침 관계를 표현하고, GNB/모달처럼 페이지 전체를 덮는 요소만 `layout.css`에 정해둔 값(헤더 100, 모달 1000 등)을 쓴다.
     - 부모에 `overflow: hidden`, `transform`, `opacity`가 있으면 자식의 `z-index`가 그 부모 밖으로 나가지 못한다. 겹침이 의도대로 안 나오면 값을 올리기 전에 부모의 이 속성들부터 확인한다.
   - **배너/히어로처럼 너비를 유동(`width: 100%`)으로 만드는 섹션은, 기본(데스크톱) 상태부터 높이도 같이 유동으로 만든다(필수).** 너비만 `100%`로 하고 높이는 원래 캔버스 기준 고정 px(예: `height: 600px`)로 남겨두면, `max-width`보다 좁고 다음 브레이크포인트보다는 넓은 중간 구간에서 비율이 어긋나 배경/이미지가 늘어나거나 잘려 보인다(실제 사례 있음). 기본 상태부터 `height: auto; aspect-ratio: {원래 가로}/{원래 세로};`로 만들어서, 반응형 오버라이드가 없는 구간에서도 비율이 항상 유지되게 한다. 태블릿/모바일 전용 오버라이드에만 `aspect-ratio`를 넣고 기본 상태를 빠뜨리지 않는다.
   - **치수표보다 먼저 노드 인벤토리를 만든다(필수). 이건 "만든 게 맞나"가 아니라 "안 만든 게 있나"를 잡는 유일한 장치다.**
     3번에서 받은 데이터로, 프레임의 **직계 자식 노드를 위에서 아래 순서대로 전부** 번호 매겨 나열하고, 각각이 결과물의 어느 섹션/요소가 되는지 1:1로 적는다. 추가 API 호출은 하지 않는다.
     ```
     | # | 피그마 노드 이름 | 결과물에서 | 처리 | CSS 파일 |
     |---|---|---|---|---|
     | 1 | _visual | <section class="sub-visual"> | 신규 | design.css |
     | 2 | _tab | <nav class="sub-tab"> | 재사용 | design.css |
     | 3 | _list | <ul class="notice-list"> | 신규 | design.css |
     ```
     `CSS 파일` 열은 **분산형 프로젝트에서만** 채운다(2번에서 판별한 결과에 따라). 통합형이면 전부 design.css이므로 이 열을 생략한다.
     - **대응이 비어 있는 노드가 하나라도 있으면 CSS 작성으로 넘어가지 않는다.** 의도적으로 제외할 노드라면(숨김 레이어, 가이드 등) 그 이유를 비고에 적는다.
     - 자식 노드가 많아 표가 길어져도 줄이지 않는다 — 섹션 하나가 통째로 빠지는 게 가장 비싼 사고이고, 이 표가 그걸 막는 장치다.
     - 완성 후 자기 점검에서 이 표를 다시 훑어 전부 실제로 만들어졌는지 대조한다.

   - **CSS 작성 전에 치수표를 만든다(필수, 추가 API 호출 없이 3번에서 받은 데이터로).**
     ```
     | 요소 | 너비 | 높이 | 비고 |
     |---|---|---|---|
     | 프로필 카드 | 475px | 416px | 고정 |
     ```
   - 여러 컬럼이 나란히 배치된 레이아웃이면, 컬럼별 (높이 합 + gap 합)이 서로 맞는지 CSS 작성 전에 미리 계산한다.
   - 요소가 한두 개뿐인 단순한 프레임이면 표를 간단히 줄여도 된다.
5. **1-3(기존 페이지) 또는 1-4(새 페이지)에서 확인/결정한 파일에 저장한다.** (다시 안 물어봄) `html/{영역}/`에 저장, `layout.css`/`design.css` 실제 갱신, 이미지는 `files/{영역}/images/common/`. **JS가 필요하다고 요청받았으면 아래 기준에 따라 `inc/{영역}/js/design.js`(공통) 또는 페이지 전용 파일로 나눠서 작성한다:**
   - **탭 전환, 아코디언, 토글처럼 여러 페이지에서 반복될 만한 단순한 공통 UI 동작**은 `design.js`(영역당 하나) 하나에 모아서 작성한다. 이미 `design.js`가 있으면 이어서 추가, 없으면 새로 만든다.
   - **배너 슬라이드처럼 특정 페이지(주로 메인)에만 있고 무겁거나 복잡한 전용 기능**은 `design.js`에 같이 넣지 않고 별도 파일(예: `main.js`)로 분리한다 — 서브 페이지가 불필요한 코드를 로드/파싱하지 않게 하고, 어떤 페이지에 어떤 기능이 있는지 파일만 보고 알 수 있게 한다.
   - **JS 파일을 만들었으면 HTML에 링크까지 반드시 넣는다(필수).** `</body>` 직전에 `<script src="/inc/{영역}/js/design.js" defer></script>`를, 페이지 전용 파일도 만들었으면 그 줄을 이어서 넣는다(공통 → 페이지 전용 순서). 파일만 만들고 링크를 빠뜨리면 아무것도 동작하지 않는다.
   - 공용 라이브러리는 기존 프로젝트의 경로를 그대로 따른다(예: `inc/lab/js/`). 새 경로를 임의로 만들지 않는다.
   - **`design.js`는 그 영역의 여러 페이지(메인, 서브 등)가 공유하는 파일이므로, 특정 페이지에만 있는 요소를 다루는 코드는 그 요소가 없는 다른 페이지에서 에러 없이 조용히 넘어가야 한다(필수).** `querySelector`로 가져온 요소가 없으면(`null`) 그 블록을 건너뛰게 방어 코드를 넣는다(예: `const el = document.querySelector('.main-hero__play-btn'); if (el) { el.addEventListener(...); }`). `null`인 요소에 바로 메서드를 호출해서 에러가 나면, 그 아래에 이어지는 다른 페이지용 코드까지 같이 멈추기 때문이다. 여러 기능을 한 파일에 모을수록 이 방어 코드가 더 중요해진다.
6. 자기 점검 후 결과를 보고한다.

## layout.css가 비어있는 첫 실행일 때

피그마에서 다음을 먼저 뽑아 `:root` 토큰으로 확정한다: 가장 많이 쓰이는 폰트 패밀리(`--font-family-base`), 자주 쓰이는 폰트 크기들(`--font-size-*`, 빈도 높은 걸 base로), 가장 흔한 line-height(`--line-height-base`), 자주 쓰이는 색상(`--color-*`). 이후 모든 컴포넌트는 이 변수만 참조한다.

회사 표준 브레이크포인트(태블릿 `max-width: 1295px`, 모바일 `max-width: 744px`)도 이 시점에 layout.css 상단에 주석으로 문서화해둔다: `/* 브레이크포인트: 태블릿 max-width 1295px, 모바일 max-width 744px (회사 표준, 프로젝트 전체 공통) */` — 실제 브레이크포인트 CSS 작성은 `pub-responsive`가 담당하지만, 토큰 문서화는 여기서 한다.

## 고정 규칙 (절대 어기지 않음)

1. **이미지/아이콘**:
   - **SVG(벡터)**: 실제 이미지 파일로 만들지 않고 `<svg>...</svg>`를 HTML 안에 인라인으로 삽입한다. `fill="currentColor"`로 색상을 CSS에서 제어할 수 있게 한다. 이건 규칙 7(인라인 스타일 금지) 대상이 아니다. **이 규칙은 페이지 안에 아이콘이 몇 개 있는지와 무관하게, 아이콘 하나하나에 개별적으로 적용된다.** 화살표, 플러스 버튼, 체크 아이콘처럼 단순한 개별 아이콘은 페이지 전체에 그런 아이콘이 수십 개 있어도 전부 다 인라인 SVG로 만든다 — "개수가 많으니 이번엔 이미지로 처리하자"고 판단하지 않는다.
   - **아이콘을 임의로 지어내지 않는다(필수)**: 피그마 참고 코드에서 아이콘/그래픽 요소가 `<svg>`+`<path>` 형태가 아니라 `<img src={...}>`(에셋 URL)로 내려오면, 그건 피그마가 그 요소를 이미지 에셋으로 제공한 것이다. "이런 모양이겠지"라고 비슷해 보이는 아이콘을 직접 지어내서 대체하지 않는다. 실제 에셋을 다운로드해서 확인한다.
   - **다운로드한 에셋이 SVG 파일이면, `<img src="...svg">`로 참조하지 않고 그 파일 내용을 열어서 인라인으로 옮긴다(필수, 실제 사고 사례 있음).** "아이콘을 임의로 지어내지 않는다"는 규칙과 "SVG는 항상 인라인"이라는 규칙이 부딪히는 지점이다 — 다운로드한 게 SVG(텍스트/XML)라면 그 내용을 읽어서 `<svg>...</svg>`로 그대로 인라인 삽입하고, 다운로드했던 파일 자체는 최종 결과물에 남기지 않는다. `<img>` + 파일 저장 방식은 **진짜 래스터 이미지(PNG/JPG)일 때만** 쓴다. "실제 에셋을 확인해야 한다"는 게 "파일로 남겨서 img로 참조해도 된다"는 뜻이 아니다.
   - **이전에 다른 페이지에서 썼던 아이콘 path를 재사용하지 않는다(필수).** "이거 예전에 만든 아이콘이랑 비슷해 보이니까 그 path 그대로 쓰면 되겠지"처럼, 지금 조회하지 않고 과거 다른 프레임에서 쓴 SVG path를 기억해서 재활용하지 않는다 — 다른 프레임이면 겉보기에 비슷해도 실제 디자인이 다를 수 있다. 아이콘마다 이번에 조회한 이번 프레임의 실제 데이터에서 나온 path만 쓴다.
   - **반복 SVG의 `id` 충돌 방지(필수)**: `<defs>`의 `linearGradient`/`mask`/`clipPath`/`filter` id가 같은 페이지에서 여러 번 반복되면 두 번째부터 깨진다. 인스턴스마다 id를 고유하게(`-1`, `-2` 등) 만든다.
   - **래스터 이미지**: 추출 가능하면 `files/{영역}/images/common/파일명`으로 저장. 불가능하면 임의로 만들지 않고 크기만 잡은 빈 영역(전용 클래스로 크기 정의)으로 처리.
   - SVG인지 래스터인지 애매하면 임의로 정하지 말고 물어본다.
   - **크롭 정확도**: 부모 프레임/여백까지 통째로 잘라내지 않고, 실제 이미지 경계와 일치하는 가장 안쪽 노드만 추출한다.
   - **크롭 검증 및 재크롭**: 다운로드 파일의 실제 픽셀 크기와 피그마 레이아웃 표시 크기를 비교, 다르면 ImageMagick/Pillow 등으로 재크롭. 좌표 판단이 애매하면 전/후 비교 이미지로 확인받는다.
   - **크기 보정**: `<img>`에 `object-fit: cover; object-position: center;` 기본 적용.
   - **`<img>` 태그에 `width`/`height` 속성을 넣지 않는다(필수).** 크기는 CSS에서 클래스로 지정한다 — HTML 속성으로 박아두면 반응형에서 크기가 바뀌어야 할 때 CSS 값과 속성값이 서로 다르게 남아 혼란스럽고, 실제로 CSS가 이겨서 속성값은 의미 없어지는데도 코드에 남아있어 가독성만 떨어뜨린다. 이미지 크기는 전부 CSS(`width`, `height`, 또는 `aspect-ratio`)로 관리한다.
   - **img/svg 크기를 여러 개를 묶는 공통(범용) 선택자로 한 번에 지정하지 않는다(필수).** `img { width: 100px; }`나 `svg { width: 24px; height: 24px; }`처럼 태그 자체를 범용으로 선택해서 페이지 안의 서로 다른 여러 이미지/아이콘에 한꺼번에 같은 크기를 적용하지 않는다 — 이러면 그 중 하나만 반응형에서 다르게 조정하고 싶어도 공통 규칙을 건드리면 나머지 전부가 같이 바뀌어버려서 개별 수정이 불가능해진다. **이미지/아이콘 인스턴스마다 각자의 전용 클래스**(`.main-hero__badge`, `.notice-panel__day-dot` 등)를 만들어서 그 클래스에 크기를 지정한다. 여러 이미지가 우연히 같은 크기를 공유하더라도, 각자 나중에 독립적으로 조정될 가능성이 있으면 전용 클래스로 분리해둔다.
   - **확장자-내용 일치 검증(필수)**: 저장 시 `file` 명령어 등으로 확장자와 실제 포맷이 맞는지 확인, 불일치 시 바로잡는다.
2. **폼/인터랙션 요소는 실제 시맨틱 HTML로 만든다**: 드롭다운은 `<select>`, 체크박스/라디오는 `<input type="checkbox/radio">`, 토글은 `<input type="checkbox" role="switch">` + `checked`/`aria-checked`. div/span으로 흉내만 내는 것 금지.
   - **접근성**: `accessibility-prompt-rules` 스킬이 있으면 WCAG 2.1 AA 기준도 같이 적용.
   - **JS 없이 작동 안 하는 요소**(탭/아코디언/모달)는 발견 시 조용히 넘어가지 않고 "마크업만 있고 JS 필요, 만들어드릴까요?"를 보고에 명시.
   - **반복·표·제목은 보이는 모양이 아니라 구조로 마크업한다(필수).** 피그마는 글자 크기만 주기 때문에 규칙이 없으면 목록이 `div` 나열로, 표가 grid 흉내로 나간다 — 이건 CSS 몇 줄이 아니라 마크업 전면 재작성이라 재작업 비용이 가장 크다.
     - **같은 구조가 2개 이상 반복되면 `<ul>`(순서가 의미를 가지면 `<ol>`) + `<li>`로 만든다.** 카드 목록, 게시판 목록, GNB 메뉴, 탭, 페이지네이션, 푸터 링크 묶음이 전부 여기에 해당한다.
     - **행과 열로 값을 읽는 데이터(요금표, 규격표, 일정표)는 `<table>`로 만든다.** `<caption>`, `<thead>`/`<tbody>`, 제목 칸은 `<th scope="col|row">`를 갖춘다. 반대로 표처럼 안 읽히는 단순 나열에 `<table>`을 쓰지 않는다.
     - **제목 레벨은 글자 크기가 아니라 문서 구조로 정한다.** 페이지당 `<h1>`은 하나(그 페이지의 제목), 섹션 제목은 `<h2>`부터 단계를 건너뛰지 않고 내려간다. 커 보인다고 `<h2>`, 작아 보인다고 `<p>`로 정하지 않는다 — 보이는 크기는 CSS로 맞춘다. 메인 페이지의 `<h1>`이 무엇인지 애매하면 규칙 12로 물어본다.
   2-1. **링크와 대체텍스트를 기본값으로 흘려보내지 않는다(필수).**
      - `href`: 같은 영역에 이미 있는 페이지로 가는 링크면 실제 경로를 넣는다. 아직 없는 페이지면 `#`로 두되 **그 목록을 보고에 "링크 미연결"로 전부 적는다** — 조용히 `#`로 채우고 넘어가지 않는다. 새 창이면 `target="_blank" rel="noopener"` + 텍스트나 대체텍스트에 "(새 창)".
      - `alt`: 로고는 사이트명, 내용이 있는 이미지는 피그마 문구나 그 이미지가 전달하는 내용. 파일명(`img_visual01`)을 그대로 쓰지 않는다. **장식용은 `alt=""`(빈 값)로 두되 속성 자체를 빼지 않는다.** 아이콘 옆에 같은 뜻의 텍스트가 이미 있으면 아이콘은 `alt=""`, 아이콘만 있는 버튼은 `aria-label`이나 숨김 텍스트를 준다.
      - **콘텐츠 이미지와 장식 이미지를 구분한다.** 없으면 정보가 사라지는 것(썸네일, 인물, 로고)만 `<img>`로 만든다. 프레임 배경 채우기, 반복 패턴 같은 순수 장식은 `<img>`가 아니라 CSS `background-image`(그라데이션이면 `linear-gradient`)로 처리한다. **단 장식이 SVG(벡터)면 규칙 1의 인라인 원칙이 우선한다** — `background-image`로 돌리는 건 래스터(PNG/JPG) 배경과 CSS로 그대로 표현되는 그라데이션에 한한다. 겹쳐진 장식 SVG 다발은 3번의 "먼저 물어본다"를 따른다.
3. **hover/focus**: 피그마에 실제로 표현된 상태만 구현, 추측 금지.
4. **클래스 재사용**: 기존 design.css 먼저 확인, 비슷한 게 있으면 재사용, 완전히 새로울 때만 신규 클래스. 애매하면 규칙 12.
   - **새 클래스를 쓰기 전에 그 이름이 이미 정의돼 있는지 `grep`으로 확인한다(필수).** 같은 선택자를 두 번 정의하면 뒤엣것이 조용히 이기고, **그 클래스를 쓰는 다른 페이지까지 같이 바뀐다** — 이번 페이지는 맞게 나오고 남의 페이지가 깨지는, 발견이 가장 늦는 사고다. 이미 있으면 재사용하거나 변형 클래스(`--변형명`)를 만든다.
   - **우선순위를 값으로 이기려 하지 않는다.** `!important`, id 선택자, 불필요한 조상 선택자 겹치기 금지. 스타일이 안 먹으면 선택자를 늘리기 전에 같은 선택자가 뒤에 또 정의돼 있는지부터 본다.
5. **클래스 네이밍**: kebab-case + BEM, 블록명 앞에 컴포넌트/페이지 접두사 필수(`.tag`, `.input` 같은 일반명 금지). 기존 무접두사 클래스 전체 리네이밍은 임의로 안 하고 규칙 12에 따라 확인. **아이콘 버튼**은 매번 `display:flex;align-items:center;justify-content:center;` + svg `width`/`height` 명시.
   - **같은 구조가 2회 이상 반복되면 클래스는 하나만 만든다(필수).** 카드 6개가 나란한 프레임에서 `.card-1` ~ `.card-6`처럼 인스턴스마다 클래스를 새로 만들지 않는다. 클래스 하나를 만들고 마크업만 반복한다. 인스턴스별로 실제 다른 값(배경색, 아이콘, 순번 등)은 변형 클래스(`.notice-card--point`)나 인라인이 아닌 CSS 변수(`.notice-card { --card-accent: ... }`를 변형 클래스에서 재정의)로 처리한다. 반복 요소를 개별 클래스로 흩어놓으면 나중에 하나만 고치려다 전부 손대야 하거나, 반대로 공통 수정이 일부에만 적용되는 사고가 난다.
   - **반복 요소 중 하나만 다르게 보이면, 그건 다른 디자인이 아니라 "상태"다(필수).** 서브 페이지 프레임의 GNB는 그 페이지가 현재 페이지인 상태로 그려져 있다 — 그 색을 `.gnb__link` 기본 클래스에 그대로 넣으면 **모든 페이지에서 같은 메뉴가 켜져 보이고**, 나중에 전 페이지 마크업을 다시 손대야 한다. 탭 중 첫 번째만 강조, 페이지네이션 숫자 하나만 채워짐, 비활성 버튼도 전부 같은 사고다.
     - **변형과 상태를 가르는 기준**: 차이가 콘텐츠 자체의 종류(카드 테마, 아이콘, 순번)에서 오면 변형 클래스(`.notice-card--point`), 현재 위치·사용자 조작에 따라 켜졌다 꺼지는 것(현재 페이지 메뉴, 선택된 탭, 비활성 버튼, 체크된 입력)이면 상태다. 애매하면 규칙 12.
     - 상태는 별도 클래스/속성으로 분리한다: 현재 페이지 메뉴는 `class="gnb__link is-active" aria-current="page"`, 선택된 탭은 `is-active` + `aria-selected="true"`, 비활성 버튼은 `<button disabled>`(+ `:disabled` 스타일), 체크된 입력은 `checked`.
     - CSS도 `.gnb__link`(기본)와 `.gnb__link.is-active`(상태)로 나눠 쓴다.
     - **서브 페이지를 만들 때는 그 페이지에 해당하는 메뉴에만 상태 클래스를 붙인다.** 공통 GNB를 복사해 오면서 이전 페이지의 `is-active`를 그대로 두지 않는다.
     - 피그마에 비활성/선택 등 다른 상태의 디자인이 따로 없으면 스타일을 지어내지 말고, 마크업(상태 클래스·속성)만 정확히 넣어두고 보고에 "상태 스타일 미정"이라고 적는다.
   - **메인 페이지와 서브 페이지의 구조가 다르면 클래스도 명확히 구분한다.** 메인 전용 컴포넌트와 서브 전용 컴포넌트를 같은 클래스명으로 섞어 쓰지 않는다 — 접두사나 블록명 자체를 다르게 해서(`main-hero` vs `sub-visual` 등) 나중에 어느 페이지에서 쓰는 클래스인지 헷갈리지 않게 한다.
   - **GNB처럼 메인/서브 공통으로 재사용하는 요소도, 실제로 메인과 서브에서 색상 등 스타일이 다를 수 있다는 걸 염두에 둔다.** "공통 요소니까 완전히 똑같겠지"로 넘겨짚지 않고, 서브 페이지 작업 시 GNB를 재사용할 때 실제로 그 페이지의 GNB가 메인과 동일한 색상/스타일인지 참고 코드로 확인한다. 다르면 페이지별 변형 클래스(`.gnb--sub` 등)로 구분해서 처리한다.
6. **색상/폰트/사이즈**: 하드코딩 금지, `var(--...)`만 참조.
   - **폰트는 토큰에 이름만 적고 끝내지 않고, 실제로 로드되는지까지 확인한다(필수).** 이름만 적고 파일이 안 불러와지면 시스템 고딕으로 떨어져서, `letter-spacing`을 정확히 옮겨도 글자 폭·줄바꿈·줄 수가 전부 달라진다. `grep -n "@font-face\|fonts.googleapis\|cdn.jsdelivr" {css} {html}`로 기존 방식을 먼저 찾아 그대로 따르고, 어디에도 없으면 임의로 정하지 말고 규칙 12로 물어본다. **분산형이면 이번에 손댄 파일만이 아니라 이 페이지가 `<link>`한 CSS 전부를 grep 대상으로 삼는다** — 폰트 선언은 공통 파일에만 있는 경우가 많아, 범위를 좁게 잡으면 없는 줄 알고 중복 추가하게 된다. **이번 페이지에서 쓴 `font-weight` 값이 전부 실제 로드되는 굵기인지도 확인한다** — 300/500을 썼는데 400/700만 불러오면 브라우저가 굵기를 합성해서 디자인과 다르게 보인다. 폰트 스택에는 대체 폰트까지 적는다. 토큰이 없으면 **통합형**은 `layout.css`에 추가하고, **분산형**은 임의로 추가하거나 하드코딩하지 말고 규칙 12로 물어본다.
7. **스타일 작성 위치**: HTML에 `<style>`/`style=""` 절대 금지. **통합형**이면 `layout.css`/`design.css`에만, **분산형**이면 2번에서 판별하고 노드 인벤토리 표 `CSS 파일` 열에 미리 적어둔 기존 CSS 파일에만 작성한다.
   7-1. **HTML 코드는 읽기 편하게 정리한다.** 태그 하나의 속성을 억지로 한 줄에 하나씩 쪼개서 세로로 길게 늘어놓지 않는다 — `class`, `id`, `aria-*`, `src`, `alt` 등 짧은 속성들은 한 태그 안에 자연스럽게 한 줄로 쓴다(전체 줄이 너무 길어질 때만 줄바꿈). 들여쓰기는 부모-자식 구조를 따라 일관되게 한다.
8. **리셋 범위 검증** (아래에서 말하는 `layout.css`는, 분산형이면 그 페이지가 실제로 로드하는 공통 CSS 파일을 뜻한다): `<p>`,`h1~h6`,`ul/ol/li`,`button`,`fieldset/legend`,`input/select/textarea`,`figure` 등 브라우저 기본 여백/테두리가 layout.css 리셋에 커버되는지 확인, 없으면 추가.
   - **`box-sizing: border-box` 전역 적용(필수)**: `*, *::before, *::after { box-sizing: border-box; }`가 layout.css에 있는지 확인, 없으면 추가.
   - **`html, body`에 `overflow-x: hidden` 안전장치를 필수로 둔다.** 개별 요소의 고정폭/좌표 문제를 하나하나 찾아 고치는 것과 별개로, `layout.css`에 `html, body { overflow-x: hidden; }`이 있는지 확인하고 없으면 추가한다. 이건 원인을 안 찾아도 되는 핑계가 아니라 **마지막 안전망**이다 — 어딘가 놓친 요소가 있어도 페이지 전체 가로 스크롤로 번지지 않고 그 안에서 잘리게 막아준다. 이 안전장치가 있어도 실제 원인이 되는 요소(고정폭, 절대좌표 등)는 위 규칙대로 그대로 찾아서 고친다 — 안전장치는 사고를 완화할 뿐 원인 수정을 대체하지 않는다.
9. **웹표준 준수**: `zoom` 등 비표준/레거시 속성, 벤더 핵 금지. Flexbox/Grid/`%`/`aspect-ratio`/`clamp()` 등 표준 CSS로 구현.
10. **긴 텍스트/실제 데이터 대비**: 고정 너비/줄수 텍스트 영역엔 오버플로우 처리 기본 적용 — 한 줄은 `overflow:hidden;text-overflow:ellipsis;white-space:nowrap;`, 여러 줄은 `-webkit-line-clamp:N` 방식. 배지/태그처럼 짧고 고정된 값은 생략 가능, 애매하면 규칙 12.
11. **요청 범위를 벗어난 콘텐츠 추가 금지**: 결과물의 모든 섹션은 (a) 이번 프레임 내용이거나 (b) 정당하게 재사용한 GNB/LNB/헤더/푸터, 둘 중 하나로 설명돼야 한다.
12. **애매한 판단**: 재사용 여부, 정보 부족, 그 밖의 임의 결정 상황은 반드시 먼저 사용자에게 물어본다.

## 생성 후 자기 점검 (사용자에게 보고하기 전에)

같은 세션에서 [자기 점검 — 규칙별 검증 표]를 빠르게 확인하는 것으로 평소엔 충분하다. `figma-review-agent`(Opus, 독립 컨텍스트)는 아래 경우에만 호출한다 — 사용자가 검증을 명시적으로 요청했을 때 / 페이지 전체를 최종 확정할 때 / 같은 프레임을 다시 요청받아 재검증할 때.

- `figma-review-agent`는 플러그인에 이미 포함되어 배포된다(`${CLAUDE_PLUGIN_ROOT}/agents/figma-review-agent.md`). 매번 있는지 확인하거나 새로 만들려 하지 않는다 — 필요할 때 Task 도구로 이름만 호출.

**토큰 절약**: 자기 점검 시 피그마 재조회 안 함(생성 세션의 스크린샷/데이터 재사용), Opus는 기본 미사용(반복 실패 시에만), 반복 최대 1~2회.

## 픽셀 단위 비교 (기본 안 함)

이 플러그인은 스크린샷 캡처/비교 스크립트를 포함하지 않는다. **사용자가 픽셀 단위 비교를 명시적으로 요청했을 때만** 그 시점에 필요한 스크립트를 만들어서 쓴다 — 미리 있다고 가정하고 실행하려 하지 않는다.

요청이 없으면 [자기 점검 — 규칙별 검증 표]와 `figma-review-agent`만으로 검증하고, 픽셀 비교 얘기는 먼저 꺼내지 않는다.

## 자기 점검 — 규칙별 검증 표 (보고 전, 이 표를 실제로 채운다)

**규칙이 많은데 검증이 없으면 규칙은 지켜지지 않는다.** 아래 표는 앞의 규칙과 절차를 검증용으로 재구성한 것이다. **표 번호는 고정 규칙 번호와 별개다** — 규칙을 가리킬 때는 "규칙 N"이라고 적는다. 눈으로 훑고 "괜찮아 보인다"로 넘기지 않는다.

**표를 그대로 출력하지 않는다 — 확인만 실제로 하고, 결과는 압축해서 쓴다.** 17행을 매번 마크다운 표로 그려내면 출력 토큰만 늘고 얻는 게 없다. 보고에 쓰는 `N`은 **이번에 실제로 확인한 행 수**다(건너뛴 행은 분모에서도 뺀다).
- **해당 없는 행은 건너뛴다.** `position: absolute`를 안 썼으면 7번, 표 데이터가 없으면 5번의 `<table>` 부분, 방향성 요소가 없으면 10번은 확인 대상이 아니다. 건너뛴 번호는 세지 않는다.
- **11번 grep 묶음은 한 번의 명령으로 몰아서 실행한다.** 여덟 번 나눠 호출하지 않는다.
- **전부 통과했으면 `자기 점검 N/N 통과` 한 줄만 쓴다.** 걸린 항목이 있을 때만 그 번호와 무엇이 어떻게 틀렸는지, 어떻게 고쳤는지 쓴다.
- 예외로 **1·2·14번(노드 누락, 텍스트 원문, 시각적 비교)은 통과했더라도 무엇을 대조했는지 한 줄씩 남긴다** — 이 셋은 판단이 들어가는 항목이라, 근거를 적지 않으면 실제로 대조했는지 알 수 없다.

`{html}`, `{css}`는 이번에 만든 파일 경로로 바꾼다.

| # | 확인할 것 | 확인 방법 | 결과 |
|---|---|---|---|
| 1 | 노드 누락 없음 | 4번 노드 인벤토리 표의 모든 행이 결과물에 실제로 존재하는지 하나씩 대조 | |
| 2 | 텍스트 원문 일치 | 피그마 문구와 결과물 문구를 항목별로 대조. 강제 개행 `<br>` 위치 포함 | |
| 2-1 | CSS 링크 구성 | 이번 페이지의 `<link>` 목록이 같은 폴더 기존 페이지와 같은 구성인지. 쓴 `var(--...)`의 토큰 파일이 그 목록에 있는지 | |
| 3 | `<head>` 뼈대 | `grep -n 'charset\|lang=\|<title>\|stylesheet' {html}` — charset·lang·title 존재, CSS는 layout → design 순서 | |
| 4 | 상태가 기본 클래스에 안 박힘 | `grep -n 'is-active\|aria-current\|disabled' {html}` — 활성 스타일이 `.gnb__link` 같은 기본 클래스가 아니라 상태 클래스에 있는지 | |
| 5 | 시맨틱 구조 | 반복 목록이 `<ul>/<li>`인지, 표 데이터가 `<table>`인지, `<h1>`이 하나이고 레벨을 안 건너뛰는지 | |
| 5-1 | 폰트 실제 로드 | `@font-face`/CDN 링크 존재, 쓴 `font-weight`가 전부 로드되는 굵기인지 | |
| 5-2 | `href`·`alt`·이미지 역할 | `#`로 남은 링크를 보고에 적었는지, 순수 장식(래스터)이 `<img>` 아닌 `background-image`인지, 남은 장식 `<img>`는 `alt=""`인지 | |
| 6 | 타이포 4속성 | 텍스트 클래스마다 `font-weight`·`letter-spacing`·`line-height`·`text-align`이 명시됐는지. 특히 `letter-spacing` 누락 여부 | |
| 7 | absolute 기준 부모 | `grep -n 'position: *absolute' {css}` — 각각의 부모에 `position: relative`가 있는지, 겹침 순서가 피그마 레이어 순서와 맞는지 | |
| 8 | `align-items` 명시 | `flex-direction: column`을 쓴 곳마다 `align-items`가 참고 코드 값으로 명시됐는지 | |
| 9 | 고정폭 vs 유동 | 참고 코드가 고정 px면 고정 px, `flex:1 0 0`이면 flex — 바꿔치기 안 했는지 | |
| 10 | 좌우/방향 | 방향성 있는 짝 요소를 레이어 이름이 아니라 실제 x좌표로 배치했는지 | |
| 11 | 코드 위생 (grep) | 아래 명령을 실제로 실행. **분산형이면 이번에 손댄 CSS 파일 전부에 대해 돌린다** | |
| 12 | 레이아웃 무결성 | 다컬럼 높이 합 일치, 페이지 전체 가로 스크롤 없음 | |
| 13 | 범위 (규칙 11) | 모든 섹션이 (a) 이번 프레임 (b) 정당한 GNB/LNB/헤더/푸터 재사용 중 하나로 설명되는지 | |
| 14 | 시각적 비교 | 3번에서 이미 받은 스크린샷과 대조(재조회 안 함). 다른 부분은 위치·정도로 구체적으로 짚고, 100% 재현 어려운 부분은 근사치임을 밝힌다. 같은 줄에 있던 요소가 분리돼 있으면 그룹핑 구조를 다시 대조 | |

11번 grep 묶음 — **한 번의 명령으로 실행한다**(나눠 호출하면 왕복만 늘어난다):

```
H={html}; C={css}; L={layout.css}
echo "-- 인라인 스타일(0)";  grep -n 'style="\|<style' "$H"
echo "-- img 크기 속성(0)";  grep -nE '<img[^>]*(width|height)=' "$H"
echo "-- id 중복(0)";        grep -oE 'id="[^"]+"' "$H" | sort | uniq -d
echo "-- 하드코딩(검토)";     grep -nE '#[0-9a-fA-F]{3,8}' "$C"
echo "-- 비표준(0)";         grep -n 'zoom' "$C"
echo "-- 리셋(1+)";          grep -c 'box-sizing\|overflow-x' "$L"
echo "-- !important(0)";    grep -n '!important' "$C"
echo "-- 중복 정의(검토)";   grep -oE '^\.[A-Za-z0-9_-]+ *\{' "$C" | tr -d ' {' | sort | uniq -d
# 위 줄은 들여쓴 @media 재정의와 복합 선택자는 못 잡는다. 이번에 새로 만든 클래스명은
# grep -n "\.클래스명" {css} 로 하나씩 따로 확인한다.
```

그 외 눈으로 봐야 하는 항목(select/checkbox/radio/toggle이 실제 시맨틱 요소인지, 이미지 확장자와 실제 포맷이 맞는지)은 따로 확인한다.

**문제 발견 시 보고 전에 고친다.** 고치고 나면 해당 행의 결과 칸을 다시 채운다. 애매하면 규칙 12.

## 완료 후 보고 형식

**단순한 섹션(컬럼 1개, 특이사항 없음)이면 짧게 한 문단으로 압축한다.**

- 생성/수정한 파일 목록 (새 페이지면 자동 결정한 파일명과 변경 가능 안내). **분산형이면 어느 CSS 파일에 무엇을 넣었는지 파일별로 나눠서 적는다**
- 자기 점검 결과 — `자기 점검 N/N 통과` 한 줄, 걸린 게 있었으면 그 번호와 무엇을 고쳤는지 (1·2·14번은 통과해도 대조 근거 한 줄씩)
- 치수표(4번에서 만든 것) — 다컬럼일 때만, 단순하면 생략 가능
- 새로 추가한 CSS 클래스와 이유(재사용/신규)
- placeholder 이미지/아이콘 목록(있으면)
- 자기 점검 발견 차이점(있으면)
- 사용자 확인 필요했던 판단(있으면)

## 보고 후 다음 진행 확인 (필수)

**이 질문은 이번 작업이 완전히 끝났을 때만 나온다.** 반응형 작업이면 웹/태블릿 완료 시점엔 나오지 않고, 모바일까지 끝나고 `pub-responsive` 최종 보고 후에만 나온다.

보고 후 그냥 끝내지 않는다. `AskUserQuestion`으로 아래 문구를 그대로 사용해서 물어본다:

- 질문: "다음으로 무엇을 할까요?"
- 선택지 1: "다음 프레임 이어서 만들기" / "다음 프레임/섹션을 이어서 생성합니다" (후보 있으면 이름도 제시)
- 선택지 2: "수정할 부분 직접 알려주기" / "어떤 부분이 잘못됐는지 구체적으로 말씀해주세요"
- 선택지 3: "이전 단계로 돌아가기" / "이미 만든 부분(예: 웹 버전)으로 돌아가서 이어서 작업합니다"
- 선택지 4: "오늘 작업 마무리" / "여기서 종료합니다"

답 없이는 다음 프레임을 알아서 진행하지 않는다.
