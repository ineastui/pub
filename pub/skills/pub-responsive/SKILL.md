> 스킬 버전: 3.3.0

# 웹 페이지에 태블릿/모바일 반응형 추가

이 스킬은 **딱 하나의 일만** 한다: 이미 있는(또는 지금 만드는) 웹(데스크톱) CSS에, 태블릿과 모바일 오버라이드를 빠짐없이 추가하는 것. 그 외의 것(폼 요소 시맨틱 처리, 이미지 규칙, GNB/LNB 재사용, 클래스 네이밍 등)은 `/pub` 스킬의 몫이니 여기서 다시 다루지 않는다.

**이미 만든 태블릿/모바일 결과를 수정하려는 요청이면(새로 만드는 게 아니라)**, 아래 순서를 처음부터 다시 밟지 않는다 — [수정 요청 처리] 섹션으로 바로 간다.

**링크는 한 번에 여러 개를 받지 않는다. 웹 → 태블릿 → 모바일 순서로 하나씩 받아서, 그 단계를 완전히 끝내고 나서 다음 링크를 요청한다.** 한꺼번에 여러 링크를 받으면 뒤쪽(특히 모바일)을 놓치는 경우가 실제로 반복됐다 — 단계를 쪼개서 한 번에 하나만 처리하는 게 훨씬 확실하다.

**"링크를 받는다"는 반드시 사용자가 직접 타이핑하거나 붙여넣은 링크만을 뜻한다.** 피그마 파일을 검색하거나 목록을 조회해서 "이게 태블릿/모바일 프레임인 것 같다"고 스스로 찾아서 쓰지 않는다 — 이름이 같은 프레임이 여러 개 있는 경우가 많아서 자동으로 찾으면 잘못된 프레임을 쓸 위험이 크다. 사용자가 링크를 주기 전까지는 어떤 노드도 조회하지 않는다.

**받은 링크가 정말 "같은 컴포넌트의 다른 크기"가 맞는지 확인한다.** 서로 완전히 다른 제목/내용을 가진 별개의 컴포넌트일 수도 있다 — 이런 경우는 반응형 관계가 아니다. 제목/구조가 아예 다른 컴포넌트로 보이면 진행 전에 사용자에게 확인한다.

**어느 프레임이 진짜 태블릿/모바일인지 애매할 때(예: 여러 후보 프레임의 너비가 서로 다르게 나올 때), px 값이나 노드 ID 같은 숫자를 나열해서 사용자에게 "이 중 어느 게 맞나요?"로 떠넘기지 않는다.** 사용자는 그 숫자만으로 판단할 근거가 없다. 대신 애매한 후보 프레임들을 **직접 다 조회**해서 실제 스타일 값(패딩, 폰트 크기, 배지 크기 등)을 서로 비교하고, 어느 쪽이 데스크톱과 같은지 / 어느 쪽이 실제로 다르게 디자인됐는지 스스로 판단해서 **결론만** 알려준다("A는 웹이랑 같은 스타일이라 태블릿 전용 디자인이 아니고, B가 실제 모바일 전용 디자인이었어요"). 그래도 진짜 판단이 안 서는 경우에만(수치를 다 비교해봐도 애매한 경우), 그때는 화면 캡처나 알아보기 쉬운 설명으로 확인받는다 — 숫자 나열이 아니라.

## 1단계 — 웹

1. **대상 CSS 파일 경로를 확인한다** (예: `inc/{영역}/css/design.css`).
2. **웹 피그마 링크를 하나 받는다.** 아직 없으면 이것부터 물어보되, 처음 요청할 때 전체 흐름을 먼저 짧게 안내한다: "반응형은 웹 → 태블릿 → 모바일 순서로 하나씩 진행할게요. 먼저 웹 프레임 링크를 알려주세요."
3. 이 링크로 가리키는 컴포넌트가 대상 CSS 파일에 이미 만들어져 있는지 확인한다. 없으면 `/pub`으로 웹 버전부터 만들어달라고 안내하고 여기서 중단한다.
4. 웹 프레임을 Figma 도구로 조회한다(해당 노드만, 페이지 전체 조회 금지). 참고 코드를 최상위부터 리프 요소까지 훑어서, 이번에 반응형을 적용할 요소들의 목록을 정리한다.
5. **이 단계가 끝났다고 사용자에게 알리고, 태블릿 링크를 요청한다.**

## 2단계 — 태블릿

1. **태블릿 피그마 링크가 있는지 먼저 확인한다.** `AskUserQuestion`으로 묻는다: "태블릿 전용 피그마 프레임이 있나요, 아니면 없어서 웹 기준으로 안 깨지지 않게만 처리할까요?"
   - **있으면**: 그 링크를 받아서 아래 2~4번대로 정확히 대조해서 만든다.
   - **없으면**: 구체적인 디자인을 추측하지 않고, 웹 레이아웃 기준 "안 깨지고 흐르는" 수준만 처리(고정폭→유동화 등). 애매하면 확인. 보고에 "태블릿 전용 프레임 없이 유동 처리함" 명시.
2. (태블릿 프레임이 있는 경우) 태블릿 프레임을 조회한다(해당 노드만). 1단계 요소 목록 기준으로 **하나하나 웹과 대조** — 부모만 보고 끝내지 않는다. 부모 배치가 바뀌었다고 자식(텍스트, 아이콘, 배지 등)도 자동 확인됐다고 넘겨짚지 않는다.
   - **최상위/전체 폭 컨테이너의 캔버스 폭을 그대로 고정값으로 옮기지 않는다(중요, 실제로 반복된 실수).** 피그마 태블릿 프레임 자체가 특정 캔버스 너비(예: 1200px)로 디자인되어 있으면, 참고 코드에 그 프레임의 최상위 컨테이너가 `w-[1200px]`처럼 캔버스 너비 그대로 찍혀 나온다. 이건 "실제 화면에서도 항상 그 값 고정"이라는 뜻이 아니다. **페이지/섹션 전체를 감싸는 최상위 컨테이너는 `width: 100%`(필요시 `max-width`도 같이)로 만든다.** 그 안의 개별 고정 크기 요소(카드, 아이콘 등)는 참고 코드 값을 그대로 유지 — "전체를 감싸는 컨테이너"와 "그 안의 개별 고정 요소"를 구분한다.
   - **고정 폭(px)과 유동 분할(`flex:1 0 0`)을 서로 바꿔치기하지 않는다.** 참고 코드가 고정폭이면 고정폭 그대로, `flex:1 0 0`이면 그대로 flex로 옮긴다 — "비슷하게 나오겠지"로 임의 대체하지 않는다.
3. 각 요소마다 `display`, `flex-direction`, `align-items`, `justify-content`, `gap`, `width`, `height`, `padding`, `white-space`를 웹/태블릿 값으로 표에 정리한다. "안 바뀔 것 같다"는 이유로 표에서 빼지 않는다.
   - **`flex-direction`이 `row`→`column`으로 바뀌는 지점은 특히 주의한다.** 부모에 `white-space: nowrap`이 걸려있으면 자식에게 상속되는데, 행→열로 바뀐 뒤에도 이 상속을 안 풀면 자식 텍스트가 카드 폭보다 넓게 밀려나고, 조상에 `overflow: hidden`이 있으면 화면 밖으로 잘려서 **텍스트가 안 보이는 사고**로 이어진다(실제 사례 있음). `column`으로 바뀌는 지점에서는 `white-space: normal`로 재설정할지 검토한다.
   ```
   | 요소(클래스) | 웹 | 태블릿 |
   |---|---|---|
   | .card | width:250px, flex-row | width:100%, flex-row |
   | .card__img | height:140px | height:140px (동일 확인) |
   ```
4. 표가 다 채워지면, **태블릿 전용 `@media (max-width: 1295px)` 블록 하나**로 CSS를 작성한다. 데스크톱 고정폭이 남아있는 요소는 표의 유동값으로 오버라이드한다. 브레이크포인트 값 자체는 임의로 바꾸지 않는다(회사 표준, `layout.css` 주석 참고).
5. **이 단계 결과를 보여주고, 모바일 링크를 요청한다.** 여기서 멈추고 다음 단계로 넘어가지 않는다.

## 3단계 — 모바일

1. **모바일 피그마 링크가 있는지 먼저 확인한다.** `AskUserQuestion`으로 묻는다: "모바일 전용 피그마 프레임이 있나요, 아니면 없어서 웹/태블릿 기준으로 안 깨지지 않게만 처리할까요?"
   - **있으면**: 그 링크를 받아서 아래 2~4번대로 정확히 대조해서 만든다.
   - **없으면**: 웹/태블릿 기준 유동 처리만. 애매하면 확인. 보고에 명시.
2. (모바일 프레임이 있는 경우) 모바일 프레임을 조회한다(해당 노드만). 같은 요소 목록을 기준으로 **웹/태블릿과 각각 대조**한다(2단계와 같은 방식, 같은 표에 모바일 열을 추가). **모바일도 태블릿과 똑같이, 최상위/전체 폭 컨테이너는 피그마 캔버스 폭(px) 그대로 옮기지 않고 `width: 100%`로 만든다** — 이건 "2단계 참고"로 넘기지 말고 모바일 단계에서도 매번 직접 확인한다.
   ```
   | 요소(클래스) | 웹 | 태블릿 | 모바일 |
   |---|---|---|---|
   | .card | width:250px, flex-row | width:100%, flex-row | width:100%, flex-col |
   | .card__img | height:140px | height:140px (동일 확인) | height:120px |
   ```
3. **모바일 전용 `@media (max-width: 744px)` 블록 하나**로 CSS를 작성한다. **태블릿 블록과 절대 합치지 않는다 — 완전히 분리된 별도 블록이어야 한다.** 데스크톱/태블릿의 고정값이 남아있는 요소는 오버라이드한다.
4. `zoom`, 반응형 목적의 `transform: scale()` 같은 비표준 편법을 쓰지 않는다. `box-sizing: border-box` 전역 리셋이 `layout.css`에 있는지 확인한다.

## 절대좌표(px)로 배치된 요소의 반응형 처리 (필수)

배너/히어로처럼 배경 그래픽이나 자식 요소들이 `position: absolute; left: Npx; top: Npx;` 같은 고정 픽셀 좌표로 배치된 섹션은, 브레이크포인트마다 **각 좌표를 수동으로 재계산해서 소수점 px 값을 다시 박아넣지 않는다** (실제 사례: 배너 안 장식 도형 5개의 좌표를 태블릿/모바일마다 일일이 비율 계산해서 하드코딩한 경우 — `zoom`과 근본적으로 같은 편법이다). 대신:

1. 컨테이너 자체를 `width: 100%; max-width: {원래 px값}; aspect-ratio: {원래 가로}/{원래 세로};`로 만들어 비율을 유지한 채 유동적으로 줄어들게 한다.
2. 안의 자식 요소들의 `left`/`top`/`width`/`height` px 값은 컨테이너 대비 **퍼센트(%)**로 환산한다(예: 컨테이너 너비 760px에서 `left: 55px`였다면 `left: 7.24%`). 퍼센트로 한 번만 환산해두면 모든 브레이크포인트에서 자동으로 비율 유지되며 적용된다.
3. 폰트 크기처럼 애매한 값은 `clamp()`/`vw` 검토, 애매하면 확인.

## 방향성 있는 반복 요소(화살표, 커넥터 등)

같은 요소가 레이아웃 안에서 여러 번 반복되는데, **위치에 따라 방향/회전이 달라져야 하는 경우**를 놓치기 쉽다. 예: 그리드 레이아웃에서 같은 행 안의 카드끼리 잇는 화살표는 가로, 다음 행으로 넘어가는 화살표는 세로로 회전된 채로 나오는 경우. "모바일에서 화살표는 다 똑같이 작아지고 숨겨지고 보이고만 하면 되겠지"로 크기/표시여부만 다루고 회전은 빠뜨리지 않는다. 참고 코드에서 같은 아이콘이라도 인스턴스마다 `rotate` 값이 다르게 들어있는지 확인하고, 다르면 `transform: rotate(...)`를 적용한다.

## CSS만으로 해결 안 되는 구조적 차이가 있을 때

기본적으로 이 스킬은 **웹 HTML 구조는 그대로 두고 CSS(미디어 쿼리)만 추가**하는 걸 원칙으로 한다. 태블릿/모바일 디자인이 웹과 근본적으로 다른 배치(요소 순서 자체가 크게 바뀌거나 완전히 다른 그룹핑)를 요구해서 CSS만으로 안 될 수 있다.

1. **먼저 HTML 안 건드리고 해결되는 CSS 기법부터 시도한다.** 순서만 바뀌면 `order` 속성, 배치 자체가 바뀌면 CSS Grid `grid-template-areas`를 브레이크포인트마다 다르게 정의.
2. **이 방법들로도 안 되면**, 임의로 웹 HTML 구조를 고치지 않는다. 사용자에게 명확히 알린다: "이 디자인은 CSS만으로 구현할 수 없습니다 — [어떤 부분이 왜 안 되는지]. HTML 구조를 바꿔야 하는데 웹 화면에도 영향 갈 수 있어 확인이 필요합니다." 동의하면 조정하되, **조정 후 웹(기본 상태)이 여전히 원래 디자인과 똑같이 보이는지 반드시 재확인한다.**

## 회귀 방지 (기존에 맞던 부분이 깨지지 않게)

웹 따로, 태블릿 따로, 모바일 따로 나눠서 작업하면, **이번에 만지는 브레이크포인트를 고치다가 이미 맞게 되어 있던 다른 브레이크포인트의 같은 클래스 규칙을 실수로 건드리는 사고**가 날 수 있다.

1. **어떤 클래스의 CSS를 수정하기 전에, 그 클래스가 다른 `@media` 블록에도 정의되어 있는지 먼저 확인한다.** 지금 작업 중인 블록만 보고 그 클래스를 통째로 다시 쓰지 않는다.
2. **수정 후, 이번에 손대지 않으려던 다른 브레이크포인트 블록들이 실제로 그대로인지 다시 확인한다.**
3. 여러 아이콘/변형 요소마다 개별 클래스(`.icon--a`, `.icon--b` 등)로 나뉘어 있는 경우, 이번에 관련된 것만 고치고 나머지는 그대로 둔다.

## 수정 요청 처리

이미 만든 태블릿/모바일 결과에 문제가 있다고 사용자가 알려주면, 처음부터 다시 만들지 않는다. 대신:

0. **판단하기 전에 먼저 기계적으로 확인한다.** 사용자가 지목한 클래스 이름으로 대상 CSS 파일을 `grep`해서, 그 클래스가 **`@media` 블록 안에 몇 번 등장하는지 센다.** 0번이면(어느 `@media` 블록 안에도 그 클래스가 없으면), 그건 판단할 것도 없이 "이 클래스는 반응형 처리가 아예 없다"는 확정된 사실이다. 이런 명백한 경우를 "다시 봤는데 괜찮아 보인다"처럼 판단으로 덮어버리지 않는다 — 셀 수 있는 사실은 세어서 확인하고, 진짜 애매한 부분(디자인이 미묘하게 다른지 등)만 판단한다. 사용자가 지목한 클래스뿐 아니라, **그 클래스를 감싸는 부모/조상 클래스**도 같이 확인한다 — 부모 자체가 미디어 쿼리 안에 없으면 자식이 아무리 있어도 소용없다.
1. **문제가 있다고 지목된 브레이크포인트의 프레임을 다시 조회한다.** 새 링크가 없으면 만들 때 조회했던 노드 ID로 다시 조회한다(새로 찾지 않는다).
2. **재조회한 데이터와 지금 코드의 대조는 같은 세션이 직접 하지 말고 `figma-review-agent`(Opus, 독립 컨텍스트)를 Task 도구로 호출해서 맡긴다.** 방금 만든 코드를 만든 사람이 다시 봐서 "괜찮아 보이는데"로 넘기는 걸 막기 위해서다. **이 에이전트에게도 0번의 grep 확인을 먼저 하라고 명시적으로 지시한다.**
3. 검증에서 나온 문제의 원인을 구체적으로 짚고, 그 부분만 수정한다. 문제없는 다른 부분까지 다시 만들지 않는다.
4. 수정 후, 왜 그런 문제가 있었는지와 무엇을 고쳤는지 보고한다. **이 보고 후에도 그냥 끝내지 않는다 — 아래 [다음 진행 확인]으로 이어간다.**

사용자가 "처음부터 다시 만들어줘"라고 명확히 요청했을 때만 해당 브레이크포인트를 완전히 재생성한다.

## 4. 완료 후 보고 (필수, 이 형식 그대로)

- 조회한 프레임의 노드 ID (웹은 항상, 태블릿/모바일은 프레임이 있었던 경우에만 — 없었다면 "프레임 없음, 유동 처리"라고 명시). **각 노드 ID 옆에 "사용자가 준 링크"라고 표시한다.** 스스로 찾은 것이라면 숨기지 말고 명시하고 확인받는다.
- 최종 완성된 대조 표 전체 (웹/태블릿/모바일 3열)
- 태블릿 `@media` 블록과 모바일 `@media` 블록이 각각 **별도로** 존재하는지 재확인한 결과
- 페이지 전체 기준으로 의도치 않은 가로 스크롤이 생기지 않는지 확인한 결과

**이 보고에 태블릿이나 모바일 관련 내용이 하나라도 빠져 있다면, 그건 이 스킬이 제대로 실행되지 않은 것이다.**
